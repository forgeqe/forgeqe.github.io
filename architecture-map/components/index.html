ForgeQE architecture

How a plain-language request becomes a run in a real Chrome browser, and a passing run becomes a reviewed test in your repo. Three processes on your machine: the Bun CLI, the agent runtime (which runs ForgeQE's agent and Scribe, the coding agent), and the Python engine. No server, no database.

The ForgeQE loop

From one sentence to a browser run, and from a passing run to a test ForgeQE has run itself.

  1. 1You type a goal, a test case key, or a request in the shell (forgeqe start) or pass it to forgeqe run.
  2. 2ForgeQE's agent (on the agent runtime, with your llms.json profile) reads it and plans which tools to call.
  3. 3It calls browser_run (or run_test_cases) on ForgeQE's local tool server.
  4. 4The tool starts a run through the engine bridge; the engine is installed on first use.
  5. 5The bridge sends the request to the ForgeQE engine on stdin and streams its events back.
  6. 6The engine drives Chrome step by step, replaying what page memory already knows and asking the model only for the rest.
  7. 7Each run writes run.json, step screenshots, workflow.yaml, and page memory under .forgeqe/.
  8. 8A passing run becomes handoff.md: steps, locators, pages, and your repo's test stack.
  9. 9Scribe, the coding agent, writes the test in your repo's own framework.
  10. 10ForgeQE runs the test itself; a browser the test never opened counts as a failure, and Scribe tries again.
  11. 11A read-only Scribe reviewer checks the test; the result lands in code.json and report.html.

Scribe, the coding agent

Scribe turns a passing browser run into a test in your repo. It runs on the agent runtime with your model, and its own claim of success never counts: ForgeQE runs the test, and a reviewer has to approve it.

  1. 1ForgeQE writes handoff.md from the run folder: the goal, each step with its locators and their confidence, the pages from page memory, the browser ForgeQE used, expected results from the test case, the browser agent's checks, the Playwright replay's result, and the names of the environment variables that hold secrets.
  2. 2Scribe starts in the repo with the active profile's model (or code.model). It reads the framework, page objects, fixtures, and helpers. What it learns is kept in scribe-notes.json.
  3. 3It ports the replay script's steps with their locators and asserts the handoff's checks. Only once a step fails does it open that page in its own browser.
  4. 4It writes the test in the repo's language and framework, extending existing page objects. Test data lives in the test, and secrets come from the environment.
  5. 5It does not run the test itself: it reports the test file and the command that runs only that test.
  6. 6ForgeQE runs that command. A failure, or an exit 0 with no browser, goes back to Scribe as the next attempt, up to code.max_attempts.
  7. 7A second, read-only Scribe session reviews the change. Its approval finishes the job, and the result is saved in code.json.

ForgeQE's agent

Reads every request and calls ForgeQE's tools. ForgeQE runs each test itself; a model's claim that it passed does not count.

Subagents

  • forgeqe Reads the request and calls the tools.
  • Browser agent One model call per new step in Chrome, inside the engine.

Tools on the local tool server

  • Browser browser_run, run_test, run_details, page_memory.
  • Cases find_test_cases, run_test_cases, read_confluence, query_api.
  • Repo write_test, heal_tests, find_tests, run_tests, list_sprints.
  • Operate monitor, logins, forgeqe_setup, push_branch, set_ci_secret.
  • Skills Loads its skills that fit the request, passes browser skills to browser_run and run_test_cases, and writes a skill into .forgeqe/skills when asked. Without them, the engine picks browser skills from the goal.

Scribe, the coding agent

Five sessions on the agent runtime, each given only the tools its job needs.

Subagents

  • forgeqe-read Learns the repo before the handoff. Reads and runs commands; no edits.
  • forgeqe-test Writes the test, with all of Scribe's tools.
  • forgeqe-review Approves the test or sends issues back. Reads only.
  • forgeqe-find Picks existing tests from the code and git history. Reads only.
  • forgeqe-heal Fixes a test the app has outgrown, or reports a bug.

Tools

  • Files read, write, edit, glob, grep. ForgeQE's own files can be read but not changed.
  • Shell Any command except git push, git clean, reset --hard, and gh repo delete. Review and find may only run git read commands and ls.
  • Live browser live_browser_* through Playwright MCP, in a Chrome set up like the run's; switched on for forgeqe-test once a step fails.
  • ForgeQE tools browser_run, run_test, run_details, page_memory, for forgeqe-heal only.
  • Skills skill loads the Scribe skills that fit the repo (built in, .forgeqe/skills, ~/.forgeqe/skills), in all five sessions; the reviewer checks the test against them too.

What Scribe does

One coding agent for writing, healing, reviewing, and finding tests.

  • Writes forgeqe code, write_test, and suites with a repo hand each passing run to Scribe.
  • Heals forgeqe heal runs the repo's tests; for each failure Scribe re-runs the flow with browser_run, then fixes the test or reports an app bug.
  • Reviews A read-only Scribe session approves the change or lists issues with the file and the fix.
  • Finds A read-only session picks tests by reading them and git history. Nothing runs until you agree.
  • Model The active llms.json profile, or code.model.

What Scribe may and may not do

It works unattended, so the rules are enforced, not requested.

  • May Edit any file in the repo, run commands, and add dependencies and config the test needs.
  • Denied git push (branches go through push_branch), git clean, reset --hard, and gh repo delete.
  • Protected .forgeqe/, forgeqe.yaml, and llms.json can be read but not changed.
  • Skills Only the skills ForgeQE's registry gives Scribe can be loaded; the runtime's own, a repo's .opencode/skills, and ~/.claude/skills (unless skills.external) stay out, and skill folders are read-only.
  • Put back Files that existed before the job and were removed or reverted are restored.

Test cases and suites

Cases come from your test system or from files.

  • Sources Azure DevOps, Jira, Xray, TestRail, Zephyr Scale, qTest, Confluence, or a local file.
  • Suites forgeqe suite runs many cases and writes one report with JUnit.
  • Step verdicts The judge gives each case step a pass or fail with evidence and a screenshot.
  • Monitor forgeqe monitor repeats runs and alerts Teams or email when a check starts failing, keeps failing, or recovers.

Page memory

Stored per site under .forgeqe/memory, never uploaded.

  • Element facts Each element the engine sees gets ranked locators with a confidence score and an identity across visits.
  • Recorded flows Passing runs are replayed on the next run without calling the model; replay stops at the first step that no longer matches.
  • Self-repair When the page changed, the model takes over from that step and the flow is recorded again.
  • Commands forgeqe memory, forgeqe memory flows, or ask the agent to show or forget a site.

What else stays on this machine

Everything ForgeQE learns is kept locally, next to your project or in your home folder.

  • Saved logins Usernames, passwords, and authenticator secrets are read from environment variables by name; the model only sees placeholders. Cookies for each site are kept in a session file readable only by you, with a .gitignore so it is never committed.
  • Scribe notes What Scribe learned about your repo's framework, page objects, and helpers, kept in scribe-notes.json for the next job.
  • Run history run.json, step screenshots, workflow.yaml, and reports under .forgeqe/. Suite reports chart the last 30 suites in the same folder.

Config and privacy

Model credentials in llms.json; behaviour in forgeqe.yaml.

  • llms.json Named profiles: provider, model, endpoint, and the name of the environment variable that holds the key. A price is per million tokens; leave currency out and reports use this machine's currency.
  • code.model / code.runtime A different model for ForgeQE's agent and Scribe, or your own agent runtime binary.
  • No telemetry The only traffic is to your model endpoint and the sites you test.

The agent runtime

What ForgeQE's agent and Scribe run on. Downloaded on first use; nothing to install.

  • Local Started by ForgeQE on 127.0.0.1 for each session and stopped with it.
  • Pinned The version ForgeQE is tested with, kept in ~/.forgeqe/tools.
  • Config in memory Model, agents, permissions, and MCP servers are passed at start.
  • Quiet Auto-update, session sharing, telemetry, and the model catalogue download are off.
