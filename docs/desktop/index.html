Desktop apps

Status: runs on Windows. The desktop job of .github/workflows/ci.yml (GitHub's windows-2022) installs the engine and the pinned UFO², replays Notepad live with the pywinauto driver and through forgeqe desktop replay, heals a moved control from the live window, and runs a whole explore: UFO² drives Notepad with a scripted model behind an OpenAI-compatible server, the action is recorded with the control's AutomationId, and the recording replays. Not yet run: explore with a real model (the job has no key), and your own apps. See Before first use on Windows.

ForgeQE drives web apps through Chrome. The desktop engine does the same for Windows thick clients (Win32, WinForms, WPF, and the native parts of Electron and WebView2 apps): say what you want in plain language, UFO² does it on the live app, and the run is saved as a YAML workflow that replays later without a model.

#Use

bash
forgeqe desktop setup --ufo                       # once, on Windows: the engine, pywinauto, and the pinned UFO²
forgeqe desktop apps                              # what forgeqe.yaml allows
forgeqe desktop explore "Create an invoice for Contoso, net 30" --app billing
forgeqe desktop record --app billing              # or do the steps yourself: no model, no UFO
forgeqe desktop replay .forgeqe/reports/desktop-explore-…/workflow.yaml customer=Fabrikam
forgeqe desktop replay workflow.yaml --data customers.csv   # once per row; the header names the variables
forgeqe desktop replay desktop-tests/ --junit results.xml   # every workflow in a folder, results for CI
forgeqe desktop replay workflow.yaml --update-baselines     # save new baselines for its expect_image steps
forgeqe desktop doctor                            # can this machine run replay unattended?
forgeqe desktop validate workflow.yaml            # any OS

Or ask ForgeQE's agent in the shell or forgeqe run: "create an invoice for Contoso in Billing and save it as a test", or "I'll show you the steps in Billing, record them". Its tools are test_apps, desktop_explore, desktop_record, desktop_replay and desktop_edit_workflow. It asks before it starts the app or takes over the desktop, and before it changes a workflow. Where it cannot ask (an MCP client), the call answers needs_confirmation until the user agrees.

Desktop apps come from the active environment in env.yaml (see HOW_TO_USE.md, "Environments and apps"), or from desktop.apps in forgeqe.yaml, which works without environments:

yaml
desktop:
  apps:
    billing:
      path: C:\Program Files\Contoso\Billing\Billing.exe
      args: ["--profile", "test"]
      # window: "Billing.*"        # for a launcher that starts the real app and exits: connect by title
  secrets: [BILLING_PASSWORD]      # the only environment variables {{secret:…}} may read
  heal: true                       # replay asks the model to re-find a control that moved (default on)
  screenshots: true                # one screenshot per replayed step (default on)

Each run writes a folder under the reports folder (desktop-explore-… or desktop-replay-…): run.json, report.html, steps/NNN.png, and for explore workflow.yaml, trace.json and UFO's own logs in ufo/. A replay whose steps were healed also writes heals.json and asks whether to write the new locators into the workflow (--accept-heals writes them without asking; with no terminal they are never written).

Behind the adapter it can be swapped for our own engine without touching the CLI, the YAML or replay.

#One model config: llms.json → UFO

UFO picks its model client by API_TYPE through ufo.llm.base.BaseService.get_service, which every model call goes through (ufo/llm/llm_call.py). The adapter adds the type forgeqe:

  • write_ufo_config writes UFO's config/ufo/agents.yaml from its template, with API_TYPE: forgeqe, the model's name, and no endpoint and no key, for HOST_AGENT, APP_AGENT, BACKUP_AGENT and EVALUATION_AGENT.
  • ufo_bridge.install makes get_service("forgeqe", …) return ForgeQEService, which calls the profile through the openai SDK (models.py): azure (key or auth: entra), openai, openai_compatible (key or Entra), and ollama through its OpenAI-compatible /v1. Keys, Azure endpoints and Entra use the browser engine's own helpers (forgeqe_engine.llm), so a profile means the same thing in both. Keys stay in environment variables.
  • Each call's time and tokens go to ForgeQE's usage ledger as the "desktop agent" (counts only, never the prompt).

Explore sends screenshots, so its profile must take images: "vision": true or false on the profile says so; without it, ollama profiles are refused and others accepted. Healing sends a screenshot only to a profile that takes images.

The request parameters suit the model by themselves: a reasoning model (o1, o3, o4, gpt-5, by the profile's model or deployment name, or "reasoning": true on the profile) gets max_completion_tokens and no temperature from the first call, and when the API refuses a parameter (max_tokens, temperature, frequency_penalty, response_format, …) the call is sent again without it, and later calls to that model leave it out (py/forgeqe_engine/model_params.py). The browser agent does the same.

#Workflow YAML (forgeqe-desktop-v1)

yaml
format: forgeqe-desktop-v1
name: Create an invoice
app: billing                 # a name from forgeqe.yaml desktop.apps, never a path or a command
variables:
  customer: Contoso
steps:
  - op: launch
  - op: click
    target: {automation_id: btnNewInvoice, control_type: Button, name: New invoice}
  - op: type
    target: {automation_id: txtCustomer, control_type: Edit}
    text: "{{customer}}"
  - op: type
    target: {automation_id: txtPassword, control_type: Edit}
    text: "{{secret:BILLING_PASSWORD}}"
  - op: select
    target: {automation_id: cmbTerms, control_type: ComboBox}
    value: Net 30
  - op: keys
    keys: ctrl+s
  - op: expect
    target: {automation_id: lblStatus}
    text: Saved
  - op: close
  • Ops: launch, click, double_click, type, select, keys, expect, expect_image, wait (at most 60 s), wait_for, close.
  • Locators use UIA properties, never screen coordinates: automation_id, name, control_type, class_name, index (when several match), and path (the ancestors' control_type and name). A target needs an automation_id or a name. Replay looks in the launched app's own windows only.
  • Variables: {{name}} from the workflow's variables or name=value on the command line; {{secret:NAME}} from the environment, only for names in desktop.secrets. A secret ForgeQE itself uses (a model key, a tracker token) is refused there. Values are substituted once and never expanded again. Targets take {{name}} too (a CSV row's {{customer}} as the control to click), never a secret.
  • Keys: ctrl, shift and alt with one named key or character (ctrl+s, alt+f4, enter, f5). The Windows and context-menu keys are refused: Win+R followed by typing runs any command.
  • Typing is literal: pywinauto's key syntax (^, %, +, ~, {ENTER}) in the text is escaped.

#Recording by hand

When you know the steps, do them yourself instead of describing a goal: no model and no UFO are involved, so it costs nothing and does exactly what you did.

bash
forgeqe desktop record --app billing --name "Create an invoice"

ForgeQE starts the app and watches the mouse and keyboard (low-level Windows hooks), asking UI Automation which control each click and key went to. Do the steps, then:

  • Ctrl+Shift+F11 with the mouse over a control adds a check: an expect step with the text it shows now (a status message, a saved total). Add one at the end, so the replay tests the outcome, not only the steps.
  • Ctrl+Shift+F12, or closing the app, finishes. The console shows each step as it is recorded.

What becomes a step:

You doStep
Click a control (two quick clicks: double_click)click with its AutomationId, name and control type
Pick an item in a drop-downselect on the drop-down, with the item's name
Type into a field (corrections and pastes included)one type with the field's text when you move on, read from the field
A key chord outside a text field (ctrl+s, enter, f5)keys
Ctrl+Shift+F11 over a controlexpect with its text
  • Passwords: a password field is never read; its step types {{secret:NAME}} (the one name in desktop.secrets, or &lt;APP>_PASSWORD, which the result tells you to set). Text equal to a desktop.secrets value is written as its placeholder. The typed characters themselves are never kept, only the field's text when you move on.
  • Only the app: clicks and keys outside the app's own process are not recorded; nor are the Windows and menu keys, or controls with neither an AutomationId nor a name. The result lists what was left out.
  • The run folder has workflow.yaml, run.json and report.html, like explore. Replay it with forgeqe desktop replay.

#Fixing a workflow from chat

When a replayed step fails because the app was slow or a dialog was in the way, ForgeQE's agent fixes the workflow with desktop_edit_workflow: it proposes the change (a longer timeout or retries on the step, a wait_for before it, a dialog button in dismiss, a healed locator, a corrected text), shows you the diff, and writes the file only when you agree. For example, after "step 4 timed out while the invoice list loaded":

text
Change invoice.yaml?
• new wait_for step before step 4
• step 4: retries 2
    - op: click
  +   target: {automation_id: btnPost}
  +   retries: 2
  • Each change has a fixed shape (set, unset, set_step, add_dismiss, insert_step, remove_step, set_variable); step numbers are the replay report's. Anything else is refused.
  • The changed workflow is checked by the engine's own validator before it is shown; one that would not run is not offered. Comments and layout are kept.
  • The old text is kept in the reports folder (desktop-edits/), and a file that changed since the edit was proposed is not overwritten.
  • The workflow must be a .yaml inside the working folder or the reports folder.

#Waits, retries and dialogs

Real apps are slow in places: a splash screen, a form that loads its data, a "Tip of the day" or "Save changes?" dialog. A workflow says how to wait for them, without fixed wait steps:

yaml
timeout: 20              # seconds a step waits for its control (default 10, at most 300)
retries: 1               # tries a failed action again, after a short pause (default 0, at most 5)
dismiss:                 # clicked whenever one of them is in the way
  - {name: OK, control_type: Button, automation_id: btnTipClose}
  - {name: "Don't Save", control_type: Button}
steps:
  - op: launch
    timeout: 90          # a slow start: how long to wait for the app's window
  - op: wait_for         # the splash screen goes away
    target: {automation_id: splashForm}
    gone: true
    timeout: 120
  - op: wait_for         # the form has loaded its data
    target: {automation_id: lblStatus}
    text: Ready
  - op: click
    target: {automation_id: btnPost}
    timeout: 60          # per step, over the workflow's timeout
    retries: 3
  • Each step waits for its control up to its timeout. click, type and select also wait until the control is enabled and visible (a form that is still loading greys its buttons out).
  • wait_for waits until a control is there, shows a text, or with gone: true has gone.
  • retries applies to click, double_click, type, select, keys, expect and expect_image. Between tries, replay pauses (1 s, 2 s, … up to 5 s) and closes any dismiss dialog. An error in the workflow itself (a missing variable) is not retried.
  • dismiss lists at most 10 targets, checked like any target. When a control is not found, or something waits to go away, replay clicks the dismiss controls that are on screen and looks again, up to 3 times per lookup. The report and the console name every dialog closed, and how many tries a step took.

#Visual checks (expect_image)

expect compares text. When what matters is drawn (a chart, a signature, a colour, a layout), expect_image compares pixels with a baseline image:

yaml
  - op: expect_image
    target: {automation_id: chartRevenue}   # without a target: the app's top window
    image: revenue-chart.png                # a file name in &lt;workflow name>.baselines/ next to the workflow
    tolerance: 0.01                         # share of pixels that may differ (default 0.01, i.e. 1%)
    ignore: [[0, 0, 120, 24]]               # regions [x, y, width, height] that change every run (a date, a clock)
  • The first run with no baseline saves what it captured and passes; the report says so. Commit the baselines folder with the workflow. --update-baselines replaces them after an intended change.
  • A pixel counts as different when a colour channel differs by more than 32 of 255, so anti-aliasing and ClearType do not fail a check. A different size (another screen scale or window size) fails with both sizes named.
  • The report shows the baseline, what was captured, and the differences in red, with the share of pixels that differ (images/NNN-baseline|actual|diff.png in the run folder).
  • Image names are file names only (letters, digits, _, -, ending .png). A path, .., or a link that leads out of the baselines folder is refused.
  • Run visual checks on one machine with a fixed resolution and scale (see DESKTOP-CI.md).

#Unattended runs

Replay needs a signed-in, unlocked Windows session. Before it starts the app, it checks the session and fails at once with the reason if it is a Windows service (session 0), a locked screen, or a disconnected Remote Desktop session. forgeqe desktop doctor runs the same check. To run the suite every night on a machine of your own, see DESKTOP-CI.md: a runner set up in the user's session (ci/desktop-runner/prepare-runner.ps1), a nightly workflow (ci/desktop-runner/desktop-nightly.example.yml), and --junit results.

#Updating UFO²

UFO² is pinned to one commit. Moving it is checked before it is pinned:

  1. The ufo-update job of .github/workflows/ci.yml runs weekly, or by hand (Run workflow, job ufo-update) with a commit. It sets up that UFO on Windows (FORGEQE_UFO_COMMIT, which takes a full 40-character commit id only), runs the adapter tests against its real code and a scripted explore of Notepad, and says in the job summary whether it passed.
  2. When it passed: bun scripts/ufo-bump.ts &lt;commit> writes the new pin into src/desktop/setup.ts, py/forgeqe_desktop/ufo_runner.py and this page. Run the tests and push; the Windows CI job tests the pin again.

When it fails, the failing step names what changed in UFO (usually the action executor or the config layout that the adapter wraps). Keep the pin until the adapter is updated for it.

#Checks of the outcome

A recording of actions only proves the steps run. When UFO has finished, and before the app closes, explore shows the model the goal and the app's controls with the text each shows now, and the model picks up to three whose text proves the goal (a status message, a saved value), by number, with the part of the text to expect. A check is kept only when that text really is in that control, so the model can choose among what is on screen but never invent it; text holding a desktop.secrets value is never offered. The checks are saved as expect steps at the end of the workflow, and the report says how many there are. With none, the report and the agent say so: add expect steps by hand.

#Recording

UFO's own step log names the control and a per-step id, not its AutomationId, so the adapter wraps UFO's ActionExecutor.execute and records each action with the UIA properties of the control it acted on. record.py turns that trace into steps: click_input → click/double_click, set_edit_text → type, keyboard_input → keys (one allowed chord) or type, select → select. Coordinate clicks, scrolls and anything else are listed as not recorded in the report. A typed value equal to a desktop.secrets value is written as its placeholder; typed text that only looks like {{…}} is kept literal, so a model told to type {{secret:X}} cannot make replay type the secret.

#Security

The YAML, the trace, the app's screen text and the model's replies can all be written by someone else. The rules in the repository's CLAUDE.md apply; for this engine:

  • No command in the workflow. app: names a desktop.apps entry: an absolute .exe (a .bat or .cmd would run through cmd.exe, which reparses its arguments) and an argument list, started with subprocess.Popen([path, *args]).
  • UFO gets UI tools only. Each explore writes UFO's mcp.yaml with UICollector, HostUIExecutor and AppUIExecutor. UFO's default CommandLineExecutor, which runs shell commands, and its Word, Excel, PowerPoint and PDF executors are left out. The adapter starts the app, so UFO never launches a program.
  • Keys: during explore the adapter refuses UFO's Windows and menu keys too, and the report lists what it refused.
  • No one at the console: UFO's safe guard asks before sensitive actions; explore answers no, since nobody is there.
  • Environment: the engine process gets system settings, the profile's key variable (or Entra's) and desktop.secrets, nothing else (desktopEnvNames).
  • Explore controls the real mouse and keyboard. It asks before starting (--yes to skip; required with no terminal). Use a test machine or VM and a test account.
  • Agent tools: a workflow path the agent gives must be a .yaml inside the working folder or the reports folder (real path, so a link out is refused); variables are names and text only; heals are reported, never written.
  • Healing: the model picks one of the window's real controls by number; control text is passed as data, and any other answer heals nothing. Heals are written into the workflow only when accepted.
  • Report: every value is escaped; images are only the engine's own steps/NNN.png and images/NNN-baseline|actual|diff.png.
  • Baselines: expect_image names are file names, and their real path must be inside the workflow's baselines folder, so a workflow cannot read or overwrite another file.
  • Unattended machines: prepare-runner.ps1 never handles a password; automatic sign-in uses Sysinternals Autologon, which stores it encrypted.
  • Install: UFO is cloned and checked out at the pinned commit (or FORGEQE_UFO_COMMIT, a full commit id only), and the checkout's HEAD is verified; replay's packages are pinned to exact versions.

#Before first use on Windows

Verified in CI: setup with and without --ufo, replay, healing, the CLI, and UFO's own code with the adapter (its config, its model calls routed to the profile, the action trace, UI tools only). Still to check, on a Windows test machine with your apps:

  1. UIA coverage: Inspect.exe shows the controls that matter with stable AutomationIds. Custom grids, Java (needs Java Access Bridge), Delphi, SAP GUI and Citrix (vision only) are where UIA falls short.
  2. Explore with your model: one goal with an Azure profile and one with auth: entra; trace.json has the controls' AutomationIds, and ufo/ has UFO's logs.
  3. Replay: the recorded workflow passes 10 runs out of 10; a renamed control is healed.
  4. Cost and time of one explore, from forgeqe usage.

Found by the Windows runs and fixed: UFO's pins need Python 3.10 (pandas 1.4.3); UFO prints emoji panels to stdout, which is the engine's event stream and crashed on the cp1252 console (now sent to stderr, characters replaced); an error in UFO's own evaluation lost the recorded actions (the trace is now kept and saved).
