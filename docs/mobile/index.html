Mobile apps

Status: the engine and its tests run on any OS, against a fake Appium server and a stand-in for Maestro. The CI job The android job of .github/workflows/ci.yml runs it on an Android emulator: Appium explores and replays the emulator's Settings app, and Maestro replays the same workflow. iOS runs the same code with the XCUITest driver, but no CI job tests it yet (it needs a macOS runner with a simulator).

ForgeQE drives mobile apps two ways, and one workflow format runs on both:

AppiumMaestro
Runsstep by step, through an Appium server (yours or a device cloud's)the whole workflow as one Maestro flow
Explore a goal with the modelyesno
Heal a control that movedyes, one model call, reported for reviewno
Visual checks (expect_image)yesno
Your team's own flowsn/aforgeqe mobile maestro, checked against an allowlist
Needsappium with UiAutomator2 (Android) or XCUITest (iOS), a device or emulatormaestro and a device or emulator

#Use

bash
forgeqe mobile doctor                                   # does the Appium server answer, is maestro installed?
forgeqe mobile apps                                     # the mobile apps of the active environment
forgeqe mobile explore "Sign in as the courier and accept the first delivery" --app courier
forgeqe mobile replay .forgeqe/reports/mobile-explore-…/workflow.yaml
forgeqe mobile replay workflow.yaml --driver maestro
forgeqe mobile replay mobile-tests/ --data couriers.csv --junit results.xml
forgeqe mobile maestro .maestro/                        # the team's flows
forgeqe mobile flow workflow.yaml                       # print a workflow as a Maestro flow
forgeqe mobile validate workflow.yaml

Or ask ForgeQE's agent in the shell or forgeqe run: "sign in to the courier app and save it as a test", "replay the courier login on Maestro", "run our Maestro flows". Its tools are mobile_explore, mobile_replay and mobile_maestro. It asks before each one starts, and desktop_edit_workflow fixes a mobile workflow after a failed replay, the same way as a desktop one.

#Apps and settings

Mobile apps come from the active environment in env.yaml, or from mobile.apps in forgeqe.yaml:

yaml
# env.yaml
environments:
  qa:
    apps:
      courier:
        kind: mobile
        platform: android               # or ios
        app_id: com.contoso.courier     # Android package or iOS bundle id
        activity: .MainActivity         # Android only, optional
        app: /builds/courier-qa.apk     # optional: install this build (.apk/.aab/.ipa/.app/.zip, https URL, bs://…)
        description: Driver app that confirms delivery
    secrets: [COURIER_PASSWORD_QA]
yaml
# forgeqe.yaml
mobile:
  driver: appium                        # appium | maestro: the default for replays
  appium:
    url: http://127.0.0.1:4723
    capabilities:                       # added to every session
      appium:udid: emulator-5554
    # username_env: BROWSERSTACK_USERNAME
    # access_key_env: BROWSERSTACK_ACCESS_KEY
  maestro:
    command: [maestro]
    # device: emulator-5554
  secrets: [COURIER_PASSWORD]
  heal: true
  screenshots: true

Each run writes a folder under the reports folder (mobile-explore-…, mobile-replay-…, mobile-maestro-…) with run.json, report.html, step screenshots, and for Maestro runs the flow, maestro.log and Maestro's JUnit report.

#Workflow YAML (forgeqe-mobile-v1)

yaml
format: forgeqe-mobile-v1
name: Courier signs in
app: courier
timeout: 20
dismiss:
  - {name: Allow, control_type: android.widget.Button}   # permission dialogs, when they are in the way
steps:
  - op: launch
  - op: type
    target: {automation_id: username}
    text: "{{courier}}"
  - op: type
    target: {automation_id: password}
    text: "{{secret:COURIER_PASSWORD}}"
  - op: tap
    target: {name: Sign in}
  - op: wait_for
    target: {automation_id: progress}
    gone: true
  - op: scroll_to
    target: {name: Deliveries}
  - op: expect
    target: {automation_id: status}
    text: Welcome
  • Ops: launch, tap, double_tap, long_press, type, expect, expect_image, swipe (direction up, down, left or right, optionally on a target), scroll_to (scrolls until the target is on screen), back, hide_keyboard, keys (enter, back, tab, delete, search), wait, wait_for, close. Timeouts, retries and dismiss work as in desktop workflows. Explore saves a tap on a system dialog (another package's control, such as Android's notification prompt) under dismiss, not as a step, so the workflow still runs where the dialog never shows; on Maestro, each dismiss target is tapped after a launch if it is there.
  • Targets use the desktop keys, mapped per platform: automation_id is the Android resource-id (with or without the package:id/ prefix) or the iOS accessibility identifier; name is the Android text or content-desc, or the iOS label; control_type is the Android class (android.widget.Button) or the iOS type (XCUIElementTypeButton); index picks one of several matches.

#Explore

The model sees the goal, its steps so far, the numbered controls on screen with the text each shows, and a screenshot when the profile takes images. It answers with one action on a control by its number (tap, long press, type), a swipe or scroll, back, or done. So it can only act on a control that is on screen. When it says done, it picks checks of the outcome from the controls' current text, kept only when that text is really there, as on the desktop. The app's text is passed as data.

#Maestro

ForgeQE workflows on Maestro. --driver maestro writes the workflow as a Maestro flow (flow.yaml in the run folder) and runs maestro test. Maestro's debug output gives each workflow step its result. Variables are filled in first. Values are matched literally, so Maestro's regular expressions never see them as patterns. A secret becomes ${MAESTRO_NAME}, which Maestro reads from the environment ForgeQE gives it, so a secret's value never lands in the flow file or on a command line. A value holding ${…} is refused, because Maestro would run it as JavaScript.

Your team's flows. forgeqe mobile maestro &lt;files or folders> checks each flow, and every flow it runs, before Maestro gets it:

  • Only UI commands pass: launchApp, tapOn, inputText, assertVisible, scrollUntilVisible, swipe, extendedWaitUntil, runFlow, repeat, retry and the like.
  • These are refused:
    • runScript, evalScript and assertTrue, which run JavaScript.
    • Maestro's AI commands, which send screenshots to a service.
    • takeScreenshot, recordings and addMedia, which read or write files.
  • ${…} may only name a variable (${USERNAME}), never an expression.
  • when: {true: …} is refused, because it is JavaScript.
  • openLink takes http(s) or the app's own deep links, never javascript:, file: or intent:.
  • runFlow files must be .yaml inside the working folder; links out of it are refused too. Nesting stops at 5 levels.

A refused flow does not run, and the error names the command.

#TestMu AI (formerly LambdaTest)

Both drivers run on TestMu's devices. Upload the app once, then use the lt:// id it returns as the app's app:

bash
forgeqe mobile upload courier.apk          # → lt://APP…  (--virtual for TestMu's emulators)

From the shell, ask in words ("upload builds/courier.apk to TestMu for courier"): mobile_upload asks first, uploads the build (it must be inside the working folder), and saves the lt:// id as that app's app: in forgeqe.yaml.

The user and key come from LT_USERNAME and LT_ACCESS_KEY (or the variables the config names), for example in a .env file in the project folder. samples/mobile-testmu/ is a ready project with TestMu's Wikipedia sample app.

yaml
mobile:
  apps:
    courier: { platform: android, app_id: com.contoso.courier, app: "lt://APP1016…" }
  appium:                                   # Appium on TestMu's mobile hub
    url: https://mobile-hub.lambdatest.com/wd/hub
    username_env: LT_USERNAME
    access_key_env: LT_ACCESS_KEY
    capabilities:
      "LT:Options": { w3c: true, isRealMobile: true, deviceName: "Pixel 6", platformVersion: "14", build: nightly }   # app: added from the app's own
  maestro:
    testmu:                                 # Maestro on TestMu, through HyperExecute
      cli: /opt/hyperexecute                # TestMu's hyperexecute CLI
      devices: ["Pixel 6-14"]               # name-version, or a pattern such as ".*-.*"
      real_device: true                     # false: TestMu's emulators
      # username_env: LT_USERNAME           # the defaults
      # access_key_env: LT_ACCESS_KEY
  • Appium needs nothing else: the Appium driver talks to the hub with the user and key from the two variables.
  • Maestro runs through HyperExecute. ForgeQE writes a HyperExecute project in the run folder and starts the CLI. The project holds the flows in their folder layout (so runFlow still works), the app (an lt:// id is passed as the device's appId; a build file is uploaded with the project), a fixed setup script (Android platform tools 35.0.2 and Maestro 2.6.1 from its release, both checked against their SHA-256) and a fixed run script, and hyperexecute.yaml. Team flows are checked against the allowlist first, as always. Flow file names may only use letters, digits and _ . - / (and one leading dot, for .maestro/), because HyperExecute's shell reads them. After the job, ForgeQE downloads its artifacts (Maestro's command results and JUnit reports), so each step gets its own result in the report.
  • Secrets on Maestro on TestMu: a workflow that types a secret is refused there for now (HyperExecute would need the value in its own vault). Replay it on TestMu with --driver appium.
  • The access key is passed to the CLI as an argument. It is removed from the CLI's output and from every file in the run folder. Neither the user name nor the key is passed to the flows' environment.
  • The testmu job of .github/workflows/ci.yml (Run workflow, job testmu) runs all three on TestMu (Appium, Maestro with a workflow, a team flow) with TestMu's Wikipedia sample app, once the repository has the secrets LT_USERNAME and LT_ACCESS_KEY.

#Security

  • No commands from the workflow or the model. app: names a configured app (a platform and an id). Appium is spoken to over HTTP, and maestro is started with an argument list, never a shell.
  • Locators go into XPath as quoted literals, so a target cannot change the query.
  • Secrets: {{secret:NAME}} reads only mobile.secrets and the environment's secrets, and ForgeQE's own keys are refused there. Explore types a secret from its placeholder, so the model never sees the value.
  • The engine's environment holds system settings, the profile's key, the listed secrets, the cloud's user and key, and JAVA_HOME / ANDROID_HOME, nothing else.
  • Cloud credentials come from the variables mobile.appium.username_env and access_key_env name; a user or key in the URL is refused. TLS is verified as usual.
  • App builds are absolute paths to an app file, https URLs, or a device cloud's own upload ids (bs://, lt://, storage:filename=); file:// and other schemes are refused.
