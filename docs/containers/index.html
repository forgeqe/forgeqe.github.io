Containers

Status: the tests run against a fake runtime on any OS. They check the commands ForgeQE builds, the checks on config, compose files, mounts and secrets, the mock stubs, and tests in a container. tests/containers.live.test.ts runs on real Docker (and is skipped without it):

  • Postgres from forgeqe.yaml and from a compose file.
  • A WireMock mock that answers a recorded run's calls.
  • A tests container that reaches the database by name and writes its results into the repository as this machine's user.

The containers job of .github/workflows/ci.yml runs both on GitHub's Docker. There, a skipped live test fails the job.

ForgeQE uses Docker or Podman, when one is installed, for five jobs:

  • Services a test run needs: a database, a queue, a cache, or the API under test. The project declares them in forgeqe.yaml, or in a docker-compose file that forgeqe.yaml names.
  • Mocks of an API: WireMock stubs made from the calls a browser run recorded, or from an OpenAPI description, so the tests can run without the real service.
  • The repository's tests in a container: run_tests runs the command the user confirmed in an image, instead of on this machine, after starting the services the tests need.
  • A workspace for the coding agents: with containers.workspace, Scribe's shell commands (build, restore, run, git) and every test ForgeQE runs for it go to a container of the project's image. The agents stay on this machine.
  • A browser in a container: with browser.provider: docker, the browser agent, the replay and Scribe's live browser drive Chromium in a container of Microsoft's Playwright image.

Scribe also has a testcontainers skill, for tests that start their own services from code (below).

ForgeQE's agent uses them through two tools, services and mock_service. The CLI has forgeqe services. When neither Docker nor Podman is on PATH, the agent isn't offered these tools.

#Use

bash
forgeqe services                     # the declared services, what runs, whether the runtime answers
forgeqe services up                  # start every declared service and wait until each is ready
forgeqe services up db queue         # just these
forgeqe services logs db --lines 50  # last lines, secrets removed
forgeqe services down                # stop and remove this project's containers (mocks included)

In the shell or forgeqe run, you can ask, for example:

  • "start the database"
  • "is the queue up?"
  • "mock the payments API from the last run"
  • "make a mock service from openapi.yaml and point order-api at it"
  • "stop the services"

The agent asks before it starts anything.

#Declaring services

yaml
# forgeqe.yaml
containers:
  runtime: docker                       # docker | podman; default: docker, else podman, on PATH
  services:
    db:
      description: Orders database for the API tests
      image: postgres:16.4              # an exact version, or name@sha256:&lt;digest>
      ports: [5432]                     # 127.0.0.1:5432 -> 5432; "15432:5432" maps another port of this machine
      env:                              # plain values only
        POSTGRES_DB: shop
        POSTGRES_USER: shop
      secrets: [POSTGRES_PASSWORD]      # environment variable names; their values come from the environment or .env
      volumes:
        - ./db/init:/docker-entrypoint-initdb.d    # read-only; a folder or file inside the project
      command: ["-c", "log_statement=all"]         # arguments for the image's entrypoint
      ready: { tcp: 5432 }              # or { http: /health, port: 8080 }; without it: the container runs
      timeout: 90                       # seconds to wait until ready (default 60)
    queue:
      image: rabbitmq:3.13.7-management
      ports: [5672, 15672]
      ready: { http: /, port: 15672 }
  mock:
    image: wiremock/wiremock:3.9.1      # the default
SettingRule
Service nameLower-case letters, digits and -, starting with a letter. Names starting with mock- are kept for mocks.
imageMust have an exact tag or a digest. An untagged image or latest is refused, because it changes under the same name.
portsAlways bound to 127.0.0.1. An address such as 0.0.0.0:5432:5432 is refused.
envPlain values on one line. Secrets go under secrets.
secretsVariable names. They are passed to the runtime by name (--env NAME), so the value is never on a command line. One of ForgeQE's own keys (a model key, a tracker token) is refused.
volumesAlways read-only. Must be inside the folder of forgeqe.yaml, and can't be the whole folder.
commandA list of arguments, never one command string.
depends_onServices to start first.
Anything elseRefused with an error, not ignored. That includes privileged, network, cap_add, devices, user, pid and the socket.

Every service, whether from forgeqe.yaml or a compose file, can list depends_on. up starts a service after the ones it depends on; a circle is refused.

#Compose files

yaml
containers:
  compose: docker-compose.yml          # or a list; inside the project

ForgeQE reads each service of the file and translates it into a forgeqe.yaml service. The same rules then check it, and a service declared in forgeqe.yaml wins over the compose file's service of the same name. Compose itself never runs.

ComposeForgeQE
imageRequired; an exact version or a digest. build is refused: build and tag the image first.
ports"5432", "15432:5432", "127.0.0.1:15432:5432", or the long form; always bound to 127.0.0.1. Any other address, and UDP, are refused.
environmentPlain values are passed as they are. KEY: ${KEY}, KEY alone in the list form, and KEY: ${KEY:-default} pass the variable by name as a secret. ${OTHER} under another name, and values that mix text and ${…}, are refused.
volumesBind mounts (./db/init:/docker-entrypoint-initdb.d) are mounted read-only, and :rw is noted. Named and anonymous volumes are left out, so the container keeps no data between runs. A path outside the project is refused when the service starts.
commandA list, or a string split into arguments (compose uses no shell, and neither does ForgeQE).
depends_onList or map form: the start order. condition is not used; ForgeQE waits until each service is ready.
x-forgeqeready, timeout, description, as in forgeqe.yaml. Without ready, a service with ports is ready when its first port takes connections.
container_name, restart, labels, healthcheck, networks, expose, deploy, profiles, …Ignored: ForgeQE names, labels and networks the containers itself.
privileged, network_mode, cap_add, devices, pid, ipc, user, security_opt, volumes_from, env_file, entrypoint, extends, …Refused, and the error names the setting.

What was left out (a named volume, a mount made read-only) is listed in notes.

#The project network

Each project's containers join their own network, forgeqe-&lt;project>, under their service name. So the API container reaches the database as db:5432, and the tests container reaches both. No other container joins the network, and no container is on the host's network. forgeqe services down with no names also removes the network.

#Tests in a container

yaml
containers:
  tests:
    image: mcr.microsoft.com/playwright:v1.48.2-jammy   # an exact version; the tests' toolchain
    services: [db, order-api]          # started first (when not running yet); the tests reach them by name
    env: { DB_HOST: db }
    secrets: [TEST_DB_PASSWORD]

With containers.tests set, run_tests runs the tests in that image unless it is called with in_container: false. Its confirmation says where the tests will run. The container:

  • Runs the command the user confirmed with the image's own shell, sh -c "&lt;command>", inside the container, never on this machine.
  • Mounts the repository read-write at its own path and works in it, so results land where ForgeQE reads them. On this machine, the tests already have the whole disk. A folder outside the repository that the results go to is mounted the same way.
  • Runs as this machine's user (--user uid:gid), so files it writes are yours. It also gets --security-opt no-new-privileges, --pids-limit 4096 and --rm, and it is removed by name when the run ends or is stopped.
  • Gets only these variables: CI=1, NO_COLOR, HOME=/tmp, the environment's FORGEQE_ACTIVE_ENV, FORGEQE_APP_* and FORGEQE_VAR_*, the saved logins' variables, and containers.tests env and secrets. Secrets are passed by name. ForgeQE's own keys are never passed.
  • Has secret values removed from its output, as on this machine.

This needs a Linux or macOS machine, because the repository is mounted at its own path.

#The workspace

yaml
containers:
  workspace:
    image: mcr.microsoft.com/playwright/dotnet:v1.63.0-noble   # an exact version; the project's toolchain
    services: [db]                       # started first; reached by name
    env: { NEXUS_ENVIRONMENT: CI, DOTNET_ROLL_FORWARD: Major }
    secrets: [TEST_DB_PASSWORD]          # by name; values from the environment or .env

With containers.workspace set:

  • Scribe's shell runs in the container. The agent runtime runs each command as $SHELL -c &lt;command>. ForgeQE sets SHELL to a script that runs the same command with docker exec … sh -c &lt;command>, in the same folder, in the workspace container. A folder outside the repository is refused, since the container has only the repository. The agent is told its commands run in a Linux container of that image.
  • Every test ForgeQE runs goes to the same image: the coding loop's runs, heal, suite's existing tests and run_tests. Each run gets its own container (docker run --rm), so stopping a run removes it. Browsers the test starts are found with docker top, as ForgeQE finds them on this machine.
  • What stays on this machine: the agent runtime, the model key, ForgeQE's other secrets, the file tools (read, edit, write; the repository is the same folder in both places), and ForgeQE's own agent, which works with you on this machine and keeps its shell here. FORGEQE_HOST_RUN=1 runs everything on this machine for a session.
  • The container:
    • one per ForgeQE process and project, forgeqe-&lt;project>-workspace-&lt;id>, removed when ForgeQE ends;
    • the repository mounted read-write at its own path; credential files in it (.env, .env.* except templates, .npmrc, .netrc, *.pem, *.key, id_* keys) covered with an empty read-only file, and .ssh, .aws, .azure, .docker, .kube and .forgeqe/sessions with an empty folder;
    • HOME on the project's volume forgeqe-&lt;project>-home, so NuGet, npm and pip caches outlive the session. Docker creates the volume for root, so ForgeQE runs chown in it once, with a fixed command;
    • this machine's user (--user uid:gid), no-new-privileges, --pids-limit 4096, the project network;
    • only CI=1, HOME, the env and secrets listed, and, in each command, the environment's FORGEQE_APP_* and FORGEQE_VAR_* and the saved logins' variables, by name.
  • containers.tests still names the image run_tests uses when it is set. Without it, run_tests uses the workspace's image.

This needs a Linux or macOS machine, as tests in a container do.

#The browser in a container

yaml
browser:
  provider: docker        # or per run: --browser-provider docker
containers:
  browser:                # optional
    image: mcr.microsoft.com/playwright:v1.63.0-noble   # default; needs Node.js and /ms-playwright
    headless: false       # default: browser.headless; a visible browser runs on a virtual display (Xvfb)
  • One container per use: each browser run (a suite runs suite.parallel at once) gets its own, and a coding job gets one that its replay and live browser share. Each is removed when its run or job ends.
  • Connection: Chromium listens on 127.0.0.1 inside the container. CDP has no authentication of its own, so a small gateway in front of it (BROWSER_SERVER in src/containers/browser.ts, run with the image's Node.js) accepts a connection only with a random 48-character token in its path, compared in constant time, and refuses a browser Origin that is not local. The port is published on 127.0.0.1 only. The token reaches the engine, the replay and the live browser's MCP server through the environment, never a file or a command line.
  • Visible or headless: a visible browser runs on Xvfb inside the container. Sites that turn headless browsers away see an ordinary one, but you do not see it on your screen. Runs keep screenshots and traces as usual.
  • Reaching the app: the container joins the project network, so a declared service is reached by its name (http://order-api:8080). An app this machine serves is http://host.docker.internal:&lt;port>; localhost is the container itself, and ForgeQE warns when a run starts there.
  • Replay: one pass, in a new browser context. The second pass (without Playwright's automation switches) needs a launch, which a running browser does not have.
  • A run explored in a container is replayed in one even when the provider is changed back later (run.json).

#Testcontainers (Scribe)

When a test needs a real service, or the repository already uses Testcontainers (Java, .NET, Node, Python, Go), Scribe loads the testcontainers skill. It reuses the repository's containers and fixtures, pins images, waits for readiness, uses the mapped port, and sets the app's own configuration from it. It never uses privileged mode, the host network, the Docker socket, or a docker command from a test. These containers belong to the tests in the repository: the tests start and stop them, wherever they run.

#Mocks

mock_service builds WireMock stubs and runs WireMock on a free port of 127.0.0.1:

  • From a run (the default: the latest run, or run_dir):
    • One stub per method, path and query of the app's own API calls, answering with the last status, content type and body the app got.
    • Other sites' calls are left out unless third_party is set.
    • Failed calls are left out.
    • Answers that were cut when recorded are listed under skipped.
  • From a description (spec: OpenAPI 3 or Swagger 2, a link or a file):
    • One stub per REST operation.
    • Each stub answers with the operation's first success status and a body from the schema's examples, or values made from its types.
    • A path parameter (/orders/{id}) matches any one path segment.
    • Instead of a description, you can give a contract set from api_contracts (set_id).
  • GraphQL, SOAP and gRPC are listed under skipped, not mocked.

A spec given as a link is fetched by ForgeQE itself, with no credentials, as api_contracts does. The stubs are written to .forgeqe/mocks/&lt;name>/mappings/. You can read and edit them there. The folder is mounted read-only at /home/wiremock/mappings. WireMock runs with --enable-stub-cors, so a web app on another local port can call it.

With for_app: &lt;api app>, the active environment's API app points at the mock for the rest of the session. That covers the API tools, and the tests ForgeQE runs, which read FORGEQE_APP_&lt;APP>_URL. env.yaml itself is not changed.

#Lifetime

  • Services and mocks the agent starts are removed when the shell, forgeqe run, or forgeqe mcp ends, as are the workspace and browser containers (forgeqe.kind workspace and browser). The home volume stays.
  • forgeqe services up keeps its services running after the command ends, until forgeqe services down.
  • Container names are forgeqe-&lt;project>-&lt;service>. &lt;project> is a hash of the project folder, so two projects never share a container. Starting a service replaces its earlier container. Removing a container also removes the anonymous volumes its image declares (a database's data folder), so nothing is left on the machine. A container is never reused with old settings.
  • Labels: each container carries forgeqe=1, forgeqe.project, forgeqe.service and forgeqe.kind. down and status look only at this project's containers.

#Security

ForgeQE's agent reads text other people control: tickets, web pages, repositories. A container command built from that text could mount the whole disk or run privileged, so:

  • No commands from the model. The agent names services that forgeqe.yaml declares, and ForgeQE builds the argument array (docker run …). It never uses a shell. Images, flags and mounts never come from a request.
  • The same restrictions for every container: --security-opt no-new-privileges, --pids-limit 1024, ports on 127.0.0.1, and read-only mounts. There is no setting to turn these off.
  • Mounts are checked like uploads (except a mock's stubs folder, which ForgeQE writes itself and mounts read-only). The path is resolved with realpath and must be inside the project. A mount that is or holds a hidden file or folder (.env, .git, .npmrc), a file named like a key (*.pem, id_rsa, llms.json) or a link is refused. A container can send what it reads anywhere.
  • Environment:
    • The docker and podman programs see only the system settings and the variables they need to find their daemon (DOCKER_HOST, DOCKER_CONTEXT, CONTAINER_HOST, …), plus the service's listed secrets.
    • A container gets only its env and secrets.
    • Logs and errors have secret values replaced with ***.
  • Not in the agents' shell: docker, podman, nerdctl, docker-compose and podman-compose are denied in the shell of ForgeQE's agent and of Scribe. So the only way to start a container is these tools.
  • Asked first: services up and mock_service ask the user before starting, as run_tests does.
