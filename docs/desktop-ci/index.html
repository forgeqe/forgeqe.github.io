Desktop in CI

Desktop replay clicks and types into real windows. It needs what a person at the machine would have: a signed-in Windows session, unlocked, with a screen. GitHub's hosted windows-2022 runners have that, and ForgeQE's own CI runs Notepad there. Your own apps usually need a machine of your own, with the app installed, its test database, and a network route to its servers. This page sets one up as a GitHub Actions self-hosted runner. The same rules apply to Azure DevOps agents and Jenkins nodes.

#What breaks a desktop run, and how ForgeQE tells you

SituationEffectFix
The runner is a Windows serviceSession 0 has no desktop; every control lookup times outRun the runner in the user's session (below)
The screen is lockedWindows sends no input to appsNo inactivity lock, no screen-saver lock
A Remote Desktop session was disconnectedThe session is lockedLeave Remote Desktop with tscon (below), or don't use it on the test machine
The machine slept or the screen turned offInput and screenshots stopPower plan: never sleep, never turn off the screen
After a restart nobody signs inNo session at allSysinternals Autologon

Before each replay or explore, the engine checks the session (py/forgeqe_desktop/session.py). On a session it cannot drive, the run fails at once with the reason, instead of timing out step by step. forgeqe desktop doctor runs the same check from a shell or a job:

text
engine   ready (C:\Users\qa\.forgeqe\desktop\.venv\Scripts\python.exe)
explore  not set up (forgeqe desktop setup --ufo)
session  1, screen 1920x1080
desktop  logged in and unlocked

It exits with 1 when the desktop cannot be driven, so a job stops before the suite runs.

#Set up the test machine

Use a test machine or VM, and a test account: the runner's jobs control its mouse and keyboard.

  1. Sign in as the account the tests will run as.

  2. Install the runner (GitHub: Settings → Actions → Runners → New self-hosted runner). Give it the label forgeqe-desktop. When config.cmd asks whether to run as a service, answer no.

  3. Run ci/desktop-runner/prepare-runner.ps1 in an elevated PowerShell (-WhatIf first to see the changes):

    powershell
    .\prepare-runner.ps1 -RunnerDir C:\actions-runner -WhatIf
.\prepare-runner.ps1 -RunnerDir C:\actions-runner

    It stops sleep, screen-off and the screen-saver lock. It turns the inactivity lock off and registers a logon task that starts run.cmd in this account's session. It warns you if the runner is also installed as a service. It never handles a password.

  4. Sign in automatically after a restart with Sysinternals Autologon, run as the test account. It stores the password encrypted by Windows. Never put the password in a script, a registry value you write yourself, or the repository.

  5. Fix the screen size. A visual check (expect_image) compares pixels, so the resolution and scale (100%, 125%) must match the machine where its baselines were saved. Set them once and leave them.

  6. Restart and check that the runner shows as idle on GitHub. Then run forgeqe desktop doctor from a job.

#Leaving Remote Desktop without locking the session

Closing a Remote Desktop window disconnects the session, and Windows locks it. To leave it running instead, hand the session back to the machine's console. In an elevated prompt inside the Remote Desktop session:

bat
for /f "skip=1 tokens=3" %s in ('query user %USERNAME%') do tscon %s /dest:console

On a VM, the hypervisor's console (Hyper-V, VMware, VirtualBox) needs no such step.

#The nightly job

ci/desktop-runner/desktop-nightly.example.yml is a ready workflow. Copy it into .github/workflows/ in the repository that holds your desktop workflows. It:

  • runs at night on [self-hosted, windows, forgeqe-desktop], one run at a time;
  • installs a pinned ForgeQE and runs forgeqe desktop setup and forgeqe desktop doctor;
  • replays every workflow in a folder: forgeqe desktop replay desktop-tests/ --junit results/desktop.xml;
  • keeps the reports, screenshots and image diffs as an artifact.

--junit writes one test case per workflow (and per CSV row with --data), which CI servers show as test results. runs.json in the output folder has the same, with the path of each report.

Secrets the workflows type ({{secret:NAME}}) come from the CI's secret store as environment variables, and must be listed in desktop.secrets or the environment's secrets in env.yaml. Pick the environment with FORGEQE_ENV or --env.

Healing calls the model. In a nightly run, either give the job the model's key so moved controls are healed and reported in heals.json (never written into the workflow without --accept-heals), or pass --no-heal so a moved control fails the run.
