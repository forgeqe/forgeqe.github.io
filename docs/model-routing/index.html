Model routing

With more than one model in llms.json, ForgeQE can give each kind of work the model it needs. A small, fast, cheap model can plan and review. A strong model can write code and find root causes. A model that takes screenshots drives the browser, and a model with a large window reads a large pull request. You do not need to know what each model can do: ForgeQE finds out.

#Turn it on

In forgeqe.yaml:

yaml
llm:
  models_file: ./llms.json
  routing: auto        # off (the default for existing projects) | shadow | auto

forgeqe init writes routing: auto for new projects. With no routing line it is off. shadow decides and logs each pick in the session log (model.route) but changes nothing, so you can see what the router would do before you let it. Shadow still runs the live checks and the rating call described below.

Whatever routing says, the model an area gets must work: its key or sign-in is set and it passed a live call (one per model, kept for a day in .forgeqe/model-checks.json once it passes; a failed one is never kept, and a failed check in model-profile.json is checked again). When it does not, the next model that works is used, a GitHub Copilot profile first, and ForgeQE says why and how to fix the first. When none works, the error lists each model with the fix. Only --profile skips this. With auto, a GitHub Copilot seat counts as costing nothing more per call, so it is picked whenever it is rated good enough.

See the picks, and every model's check with its fix:

text
forgeqe models --routes

#The areas of work

AreaWhat runs in itNeeds
agentForgeQE's agent: the shell, forgeqe run, forgeqe mcptool calls; rated 4+
browserBrowser, desktop and mobile runs, from screenshotsimages; rated 4+
codingScribe writing and healing tests, API teststool calls; rated 5
reviewTest reviewer, pull-request review, evaluation judgetool calls; rated 3+
analysisRoot cause of defectstool calls; rated 5
planningRefine, finding tests, API scenarios, exploratory charterstool calls; rated 3+

#How a model is picked

  1. Your choices win. --profile (or WP_LLM_PROFILE) and code.model keep the router out. A profile pinned in llm.routes is used for its area. code.review_profile still sets the reviewer.

  2. Facts rule models out. The router never picks a model that:

    • has no key, or failed its live check;
    • takes no images, for browser work;
    • takes no tool calls, for agent work;
    • has a window too small for the prompt (a large pull-request diff, for example).

    The facts come from llms.json, a live check, and the public model lists (models.dev and LiteLLM) that ForgeQE already downloads for prices. A fact that nobody knows never rules a model out.

  3. Ratings pick among the rest. The cheapest model rated at the area's bar is picked. Writing code and finding root causes ask for 5, because a weaker model there costs more in failed attempts than it saves. If no model reaches the bar, the best-rated one is picked. With no ratings yet, the active profile is kept unless a fact rules it out.

  4. A failed answer escalates once. When a root-cause analysis finds nothing, or finds a cause with low confidence although it could read the product's code, it runs again on a stronger model: one rated higher for the area, or rated the same and priced higher. Both runs are counted in its cost.

The same configuration and task always give the same model. A pick changes only when the models, the ratings or the size of the prompt change. Each pick is shown once ("Model for planning: mini (…)") and is written to the session log.

#How ForgeQE learns the models

The first routed call in a project with two or more usable profiles does this once:

  1. A live check of each model (python -m forgeqe_engine probe): one short structured answer and one image. This finds a deployment that does not exist, a wrong key, and whether the model really takes images. It also measures how fast the model answers.
  2. One rating call. The active profile's model receives the facts of every model, never a key, an endpoint or an account. It rates each model 1–5 for each area and gives it a tier (fast, balanced or strong).

The result is kept in .forgeqe/model-profile.json next to forgeqe.yaml. ForgeQE uses it until the profiles in llms.json change (provider, model, deployment or endpoint). You can edit the ratings. ForgeQE keeps your edits while the profiles stay the same. It checks the file every time it reads it: names that are not profiles and unknown areas are dropped, and ratings are rounded to whole numbers from 1 to 5.

The live checks reach every profile in llms.json that has a key, whatever llm.routes pins. A pin keeps your runs' data on one deployment; the checks carry nothing from your runs. To send nothing to the other profiles at all, use routing: off, keep one profile with a key, or pass --profile.

To check and rate again (for example, after a deployment changed its model):

text
forgeqe models --routes --profile-models

#Limit what an area may use

yaml
llm:
  routing: auto
  routes:
    browser: [gpt4o, gpt54]   # only these two, the router picks between them
    coding: gpt54             # pinned
    planning: auto            # any configured model (the default)

A name in routes must be a profile in llms.json, and an area must be one of the six above. Anything else stops ForgeQE at start with a message that names it.

#What it does not do

  • ForgeQE's agent picks its model when its session starts and keeps it for the whole conversation. Changing the model mid-conversation would drop the prompt cache and make every later turn cost more. The agent hands heavy work to the other agents, and those are routed.
  • A rating is one model's judgement. It is kept in a file that you can read and correct.
