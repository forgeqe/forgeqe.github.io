Architecture

Three processes. The Bun CLI owns the shell, config, profiles, and ForgeQE's tools. ForgeQE's agent runs on the agent runtime, reads each request, and calls those tools over MCP. Scribe, the coding agent, runs on the same runtime and writes, heals, and reviews tests. A Python engine drives Chrome; three more drive Windows apps (py/forgeqe_desktop, on UFO² and pywinauto), Android and iOS apps (py/forgeqe_mobile, on Appium and Maestro), and the team's databases (py/forgeqe_data, on SQLAlchemy, sqlglot and DB-GPT, in its own environment). There is no FastAPI server, and ForgeQE keeps no database of its own: the databases it reads, and writes to when one is marked writable and the user confirms, are the ones databases: names.

The single-view map of subagents, tools, and capabilities is forgeqe-architecture.html (forgeqe docs --open). Suite report.html includes the browser agent's token counts, and a cost in the machine's currency when the profile has a price.

Saved logins. The request carries each login's name, domains, and environment variable names; values cross stdin only for logins remembered this session (values), and are never logged. use_logins builds the engine library's domain-scoped sensitive_data ({domain: {shop_username: …, shop_password: …, shop_bu_2fa_code: &lt;TOTP secret>}}), so the model sees placeholders, the engine fills values only on matching domains, masks them in page text, and turns bu_2fa_code into a fresh pyotp code when typed. Session files for the run's logins are merged into Browser(storage_state=…). Because the agent closes the browser when run() returns, _on_step_end saves each login's cookies and origins (_cdp_get_storage_state, split by host) whenever they change, mode 0600, with a .gitignore in the folder. Page memory records text_env / totp_env instead of values, so replays and the handoff to the coding agent (process.env.X) use the current secrets.

Session logins (src/sessionLogins.ts). Credentials the user gives in a message or test case become a login through the logins tool's remember action: the site and its sign-in hosts as domains, FORGEQE_&lt;NAME>_USERNAME / _PASSWORD / _TOTP as env names, a session file in .forgeqe/sessions/, and the values held in ForgeQE's process only. executeRun sends allLogins(config) (forgeqe.yaml's plus these, a remembered one replacing a configured one of the same name) and passes the goal through redactSecrets, which replaces each remembered password or secret with "(the password of saved login NAME)". runTestCommand puts the values under their env names for ForgeQE's own test runs and redacts them from the output. The brain's notes list remembered logins; its prompt says to remember credentials before the first run and never put them in goals.

Step budget. max_steps is a checkpoint, not a wall. The library's run() gets 3 × max_steps, so its budget warning (at 75%) and forced last-step done come at the cap. At each multiple of max_steps, _on_step_end looks at the last 10 steps (step_outcomes: the step's actions ran without an error and the agent's own evaluation at the next step did not call it a failure) and carries on when at least 3 worked (making_progress), logging "Reached N steps and still making progress"; otherwise it stops the agent and the summary starts "Stopped at N steps: the last 10 steps made no progress." Page loading. _on_step_start calls settle_page before every step after the first: it reads location.href, document.readyState, and the body's text length over CDP every 0.25 s until the page is complete, or interactive with content, for up to 8 s (3 s while the tab stays about:blank), and logs a debug line when it waited a second or more. The library switches to a tab a click opened 50 ms after the click and waits at most 0.3 s before reading the page, so a heavy page used to be read blank and cost a step. The agent's own note actions (write_file, replace_file, read_file) are in READ_ONLY_ACTIONS, so they are neither recorded nor stop a replay.

Repeated controls. _control_loop_exceeded counts the same click, input, search, or select (by element index or text) in the last 8 steps. The first time one reaches 4, the agent is not stopped: _install_nudges wraps the library's _inject_loop_detection_nudge, which runs after the library clears its per-step context, and the next step's prompt gets "you have done click "One way" 4 times… work out why the earlier attempts did not stick… take a different approach". Counting restarts after the nudge; reaching 4 again stops the run ("…after the agent had already been told to change approach"). With a library that has no such hook, the first loop stops the run as before.

Resuming a failed run. Each recorded step keeps the agent step it came from (MemoryRun.step_of; 0 for replayed steps and the opening navigate). On a failure other than a user stop, resume_point picks the step where the run went wrong: where a repeated-control loop began, where the last progress window of a stalled run began, or the trailing streak of failed steps. resume_steps keeps the recorded steps from before it (not only navigation and waits). They go to resume.json in the run folder and under resume in the task's flow file; a later success removes them. Replay then picks, in order: the request's resume (from browser_run's resume_from), the task's successful flow, the task's resume. handoff_task(kind="resume") tells the agent where the earlier run went wrong and to take a different approach there. A run that failed because an expected result did not hold (outcome: assertion_failed) keeps the steps up to that check instead (assertion_resume: MemoryRun.first_failed_check finds the earliest check recorded with holds: false, by the flow steps done and the agent step when it was recorded), marked assertion: true; the next run replays them and the handoff tells the agent to check that result again on the page as it is, record it as not holding if it still does not, and not to redo the steps or try other ways to make it true. That is what a reproduce run or a rerun of a failing case needs: the way to the failing check, not another exploration. The resume also keeps that check (check: expected, and the text the page showed instead) unless a passing check of the run found the same text. With checks_first and replay: verify, reproduced_by_check lets the run look for that text right after the replay with no model: found, the run ends assertion_failed with 0 tokens (trace source memory_reproduced) and keeps the resume; not found, the agent takes over with the handoff above. Checkpoints. After each step _on_step_end calls MemoryRun.checkpoint(): the steps so far (resume_steps with no cut-off) go to checkpoints/&lt;flow file name> in the memory folder (a separate folder, so recent_flows never lists them) with the run id and interrupted: true, the same data goes to the run folder's resume.json, and page memory is flushed. MemoryRun.finish removes the checkpoint when this run or the run it picked up wrote it, except for a stopped run; _write_artifacts removes the checkpoint resume.json from a run that did not fail and was not stopped. The lookup takes the checkpoint after the task's successful flow and before its saved resume, as kind="interrupted", and handoff_task then says the earlier run was cut off and to carry on without repeating the steps. Stopped runs report tokens from the library's token counter, since history.usage is only filled when run() returns. Session-login values are also set in the engine process's environment (one process per run), so a replayed sign-in step finds them by env name.

Session log (src/sessionLog.ts). main() opens one log per session for the commands that run something (startSessionLog, in the logs folder next to sessions). Lines are &lt;ISO time> &lt;kind> &lt;JSON>: session (versions, argv, profile, browser and memory settings, login names), agent.ask / agent.turn (written after the turn, so credentials the message gave are remembered and redacted), agent.event (the agent runtime's events), tool.call / tool.result (from createMcpServer, with duration), tool.event (what a tool reports while it runs: the coding and healing agents' reads, commands, edits, and test runs, suites, cards; browser run events are left to engine.event), engine.request / engine.event / engine.log (every stderr line) / engine.exit (from runEngine), run.done (from executeRun), and error. serialize hides fields named like api_key, password, token, or values, clips strings at 8,000 characters (200,000 with --debug), and redactForLog replaces remembered login values, secret-looking environment variables (name parts KEY, TOKEN, SECRET, PASSWORD, PAT, CREDENTIALS, values of 8+ characters), and API keys from llms.json. --debug / FORGEQE_DEBUG also sets the engine's logging level to debug; debug-level engine events go to the log only. bundleLogs (forgeqe logs bundle, /logs) stages the log, the run folders named by out_dir / runDir / run_dir in it (text files redacted, screenshots only with shots), forgeqe.yaml, profiles without keys, and versions, then tar -czfs them.

Updating (src/update.ts, forgeqe update). findInstalls walks PATH for forgeqe executables, resolves pyenv shims with pyenv which, and classifies each by what it resolves to: a package folder named ForgeQE under .bun (bun) or elsewhere (npm), or a script whose shebang is a Python that imports forgeqe_cli (pip). latestVersion reads the registry's latest tag with a cache-busting query; npmReady needs the version document and a HEAD of the tarball to answer 200, pypiReady the PyPI version JSON, because both registries accept an upload minutes before they serve it. update waits for them (waitUntil, every 15 s, 20 minutes by default), then runs and,, or, and reads the installs again to confirm. scripts/publish.sh waits the same way after uploading before it prints Done.

Step verdicts. When the goal came from a test case with steps, CASE_REPORT_INSTRUCTION goes into the system prompt and output_model_schema=CaseReport makes the engine library's done action return {summary, steps: [{step, status, actual}]}; history.structured_output becomes case_report in the result. If the Agent rejects the schema, the run continues without it.

Finishing and the judge. _GOAL_VERIFICATION_SYSTEM_MESSAGE is added to every agent's system prompt: done with success only when every field holds exactly what the goal asked for (pre-filled or extra values in multi-value fields removed), every setting the goal names is applied through the page's own controls and shown by the page, and findings are read from the page, items a list already shows are read from it in one step, and a tab that looks blank right after opening is still loading. The engine library's judge (use_judge) is off by default: browser.judge: true (passed to the engine as its judge setting) or FORGEQE_ENGINE_USE_JUDGE=1 turns it on, and it then makes one model call over the steps and screenshots. It was turned off because it failed completed runs whose answer came from one screenshot (five result scores) instead of one step per item, and ForgeQE's agent then retried with ever stricter goals. When the agent says success and the judge's verdict is false, the run fails with the judge's failure_reason ahead of the agent's report; the verdict goes into run.json as judge. A judge call that errors leaves the agent's result as it was.

Window and video. window_launch_kwargs sizes a local browser from browser.viewport: the page when headless, the window with browser.window: viewport. Otherwise a visible window opens screen-sized (the engine library's default) and, before the first page, maximize_window sets windowState: maximized over CDP. With browser.video on (the default), the browser is started before the replay or the agent, and start_video starts the library's recording watchdog on &lt;run>/video.mp4; stop_video finishes it before the browser closes, and run_with_events adds it to the run's files. The watchdog encodes Chrome's screencast frames at 30 fps as they arrive, so the video's timing follows how often the page repaints, not the clock. The encoder (browser-use[video]: imageio with ffmpeg, numpy) is installed with the engine, and added to an engine set up before it. The report lists video.mp4 among the run's files and plays it on the Artifacts tab.

Browser profile. At the end of the first step (or before writing a trust-mode replay), browser_profile reads how the browser was set up: the engine's driver, channel and executable, headless, the default switches removed, extra HTTP headers (none), Browser.getVersion, and from the page navigator.userAgent, navigator.webdriver, language, time zone, and viewport. It goes into run.json as browser, and the handoff shows it so the coding agent can compare its test's browser with it.

Timeline. build_timeline writes steps.json from the history (and the replayed steps): URL, title, the model's evaluation, memory and next goal, each action with its error, start time (t0) and duration, the part of it spent waiting for the model (model_ms, from wrapping llm.ainvoke and overlapping the calls with the step's step_start_time/step_end_time), and a JPEG of the page (max 1280 wide) under steps/, subject to report.screenshots. Each action on an element carries box: the element's absolute_position from the DOM snapshot the model saw, minus the page's scroll, as fractions of the viewport, so the report can outline it on that step's screenshot. Timeouts, stops, and crashes still write it from the partial history.

Diagnostics. Diagnostics registers Runtime.consoleAPICalled, Runtime.exceptionThrown and Log.entryAdded on the engine library's CDP client (cdp-use allows one handler per event, and the engine library's own watchdogs don't use these three; Network.responseReceived belongs to the downloads watchdog, so failed and slow requests come from the page's resource timing entries, responseStatus and duration, at each sample). It samples at every step start and end and after each replayed step. Each new page (by URL without the hash, up to 25) is checked once: Accessibility.getFullAXTree for unnamed buttons, links, fields and images, heading order and the document title, plus a page script for lang, text contrast (WCAG ratios, skipping text over images) and zoom-blocking viewports, with up to five examples each from DOM.getOuterHTML. A request counts as slow from 3 s. assign_problems attaches each event to the step it happened in (by t0), at most 25 per step; run.json gets the totals as diagnostics, and the pages go to accessibility.json. report.accessibility: false skips the page checks.

Overlay. With a visible browser and browser.overlay on, brand.Overlay puts a &lt;forgeqe-overlay> element on each page: a shadow root (page CSS can't reach it) with an edge glow, a bottom bar (icon, the step from step_text: its intent from next_goal, or the "next goal" sentence in the model's memory, and its actions in words from plain_action, never raw tool parameters; a Thinking / Acting / From memory chip), and a transparent blocker. Window capture listeners, added before the page's scripts, drop trusted mouse, wheel and key events while it is locked. It locks in _on_step_end and replay's gaps between steps, and unlocks in _on_new_step (which the engine library calls after the model answers and before the actions run) and around each replayed action, so the agent's own CDP input always gets through. Each page gets it from Page.addScriptToEvaluateOnNewDocument on its own target (the engine library's _cdp_add_init_script covers only the focused one), with the current text baked in and the lock off, since a page can load halfway through a step's actions. The host carries the library's DOM-exclude attribute (left out of the DOM the model reads), aria-hidden, and attached outside &lt;body>, so the accessibility checks skip it. brand.install() wraps ScreenshotWatchdog.on_ScreenshotEvent to hide it for every screenshot (the model's and the report's) and replaces the about:blank watchdog's animation, which loads a logo from the library's CDN, with a start page. The status bar's icon is raw pixels on a canvas, so a page's img-src policy can't block it or log an error; the start page only appears on about:blank, which has no policy. Headless runs skip all of it.

Left out: Mongo persistence, LangGraph, Scrum Studio, and video recording. Nexus's Mongo site memory and compact replay are replaced by the file-based page memory below.

The model decides everything about navigation. With no pinned URL the browser starts blank and the agent opens the site itself, even when the goal names one. Nexus's _infer_initial_url_from_goal regex is removed, and the engine library's own URL guessing from the task (directly_open_url) is turned off. Only a pinned start URL (--url, start_url, or the start_url argument the agent passes when the user named a page) is opened before the agent's first step.

fd 1 inside the engine is redirected to stderr at start-up, so library prints cannot corrupt the event stream.

#The path a test follows (capture.py)

A passed run becomes a test, so the run records the path that worked, checked while the page is still there, not every attempt.

What changed. install_effects wraps the agent's tools.act. Around each click, key press, script, and click_selector it takes a fingerprint of what a user could notice (address, visible text, element count, open menus and dialogs, form values, selected and pressed states) and polls for up to 1.5 s for a change. _record_memory_results leaves an action that changed nothing out of the flow (a click on a decorative node, a retry that missed, a script that only read the page) and lists it in run.json memory.left_out; fills and selects always stay. A script that did change the page stays, marked scripted, and the handoff asks for the page's own control instead.

The control, and locators checked on the live page. Before the step's actions run (the library's new-step callback comes before multi_act), _point_at_controls re-points each element action from the node under the pointer to the control a user acts on (an icon inside a label or button becomes the label or button) and verify_locators checks each candidate on the live page: role and name through Accessibility.queryAXTree (the accessible names Playwright's getByRole uses), ids, CSS, attributes, text, and XPath in the page. A locator is verified when it finds exactly that element (or something inside it). Verified locators come first, so best_locator is one that worked.

Real clicks, not scripts. The agent's prompt (CAPTURE_SYSTEM_MESSAGE) asks it to act only through browser actions, and click_selector gives it a real mouse click (scroll into view, refuse when covered, Input.dispatchMouseEvent) on an element it found by CSS, captured like any click.

Checks with their element. record_check finds the smallest visible element showing the text and the section it sits in, each with verified locators (element, container in workflow.yaml checks), and takes dynamic for live data (today's date, a price, a count).

The handoff lists the path with ✓ on verified locators, says how many actions were left out, gives each check its locator and section, and leaves out page memory when every step and check is verified. Scribe is told to use ✓ locators as given and not to look for those elements again.

#Page memory (memory.py, replay.py)

Files under memory.dir (default .forgeqe/memory next to forgeqe.yaml, or ~/.forgeqe/memory when there is no config file), written atomically at the end of a run:

  • pages/&lt;host>/&lt;path>.json: one per page template. The key is host (plus port) and path; segments that are numbers or look generated become *, and the query string is dropped. Each element stores tag, role, accessible name, text, stable attributes (never value), its locators, best, confidence, visit and use counts, and first_seen / last_seen / last_used / last_updated. Pages keep at most 400 elements; past that, elements never used and least recently seen go first.
  • flows/&lt;goal>-&lt;hash>.json: keyed by the normalised goal and start URL. It holds the steps of the last successful run, each with the element's top locators and a fingerprint, plus pass, fail, and replay counts.
  • scribe-notes.json: written by the coding side (src/code/notes.ts), not the engine: per repository, Scribe's notes from its reading turn and the tests jobs wrote there.

Observe. Before each agent step, _on_new_step passes the engine library's selector_map (EnhancedDOMTreeNodes) to MemoryStore.observe. For every element it builds the locator candidates, counts how many elements on the page each one matches, and merges them into the page file. An element keeps its identity across visits through a strong locator (test id, id, name, role, label, placeholder, href), then its XPath, then a hash of tag and anchor text. An XPath match counts only when the role and accessible name (or text) agree too, because sites reuse one popup container for different widgets; an element whose label changed becomes a new entry. When replay resolves a step on a different entry than the one recorded, record_stale marks the recorded entry's dead locators as missed and failed, and the flow is saved against the new entry. flow_step lists the locators that matched on the page at that moment ahead of those only seen on earlier visits.

Confidence is 100 × base × uniqueness × stability × reliability, clamped to 1–99:

FactorValue
baseby kind: test id .96, id .90, role .88, name .86, label .84, placeholder .82, alt .78, href .74, title .72, text .70, CSS .50, XPath .30; ×0.4 when the value looks generated
uniqueness1 when it matches one element, else 0.5 / (matches − 1)
stability(0.75 + 0.25 × min(seen, 4) / 4) × seen / (seen + missed)
reliability(successes + 1) / (successes + failures + 1)

Record. _on_step_end pairs each action's result with the element it targeted. It records success or failure against the element and the locator, and adds non-read-only actions to the run's flow. At the end, a complete run replaces the flow's steps, a failed run only counts a failure, and a stopped run leaves the flow alone.

Replay. Before the agent is built, replay_flow runs the stored steps with Tools().act, the same actions the agent would call. In order, the run replays the exact goal's flow, a failed run's resume steps, a cut-off run's checkpoint, or an edited case's unchanged steps. A goal with none of these gets the start it shares with another task on the host (MemoryStore.shared_start, kind shared): flowmatch.shared_start (py/forgeqe_engine/flowmatch.py, no model) ranks the host's passing flows by the content words their goals share with this one, and of the three most similar keeps the longest leading run of steps this task may borrow. A step is borrowed when this goal names its control or the value it types; when it signs in with a saved secret (and the click that submits that sign-in); when it clears a cookie banner or pop-up; or, while the flow is still in its opening, when another recorded task on the host took the same step without a value. Values another task typed, page scripts, uploads and API calls are never borrowed, a flow that opens another URL than this task's start is not used, and the first step that fails these rules ends what is borrowed. handoff_task(kind="shared") names the task they came from and tells the agent to check the page fits and carry on. prompt_hints still lists the steps of up to 2 recent flows of other tasks and the controls that worked there. Element steps take a fresh snapshot (retrying briefly while the page loads) and resolve the element by the store's current best locator, then the step's own locators, then the fingerprint. Read-only actions (extract, find_text, done, …) are skipped. Replay stops at a step it cannot resolve or restore: password fields, file uploads, tab switches, evaluate. An api_request step is replayed with the same call in the page's session (register_api_request on replay's own tools), and stands only when the server answers with the recorded status (api_mismatch); otherwise replay stops there and the agent judges the answer. handoff_task then tells the agent what was already done: check and finish (verify), or continue from the stopped step. trust returns success with no agent only when every step of this same task ran. Replayed steps are emitted as step events with "source": "memory", before any agent steps. A replayed step whose recorded locators no longer match anything on the page, but that still resolved through another locator, is recorded as a heal ({step, line, label, stale, used}); when replay stops and the agent then finishes the case, run.json notes repaired with the step and reason. Both go under memory in run.json for the report.

Parallel runs. flush and save_flow_result hold an fcntl lock on &lt;memory>/.lock. Each page file has a revision counter. If the file on disk has moved on since this run loaded it, the run merges instead of overwriting: every visit, match, miss, success, and failure counter becomes the saved value plus this run's own change, elements this run never saw keep the saved copy, and the revision becomes one past the higher of the two. Two runs on the same page (a suite with parallel above 1) therefore both count.

Hints. prompt_hints adds the last successful steps on the same host, and the controls those runs actually used, to the agent's extended system prompt, capped at 2,500 characters, and tells the agent to act on them in one turn. The system prompt cannot name an element's index, which changes with every page load, so on its own it left the agent reading the whole element list anyway. Known controls per step. _install_known_controls wraps the library agent's _prepare_context: after the library has built the step's page message, MemoryStore.observe records the page once (the snapshot is shared with the step callback through step_seen, so a step is observed once), and MemoryStore.known_controls adds a context message naming up to 10 controls on this page that earlier runs acted on with success, each with its index in this step's element list ([12] Email address * (textbox, worked 2×)), told to act on them by index in this turn. A page memory has never acted on adds nothing. Context messages are the library's own per-step channel (its loop nudge uses it), cleared before each step.

In-run history. Fast mode passes max_history_items=8 and turns message compaction off. Each later step of an exploration keeps the first step and the most recent ones, instead of resending the whole transcript or pausing for a summary model call. FORGEQE_ENGINE_MAX_HISTORY_ITEMS overrides the cap (minimum 6, which is the engine library's own floor).

Workflow steps. compact_step gives each workflow step its best_locator and ranked locators (with css/attr where the locator needs them), evaluate steps their code, and every step the browser agent's note, which the handoff passes to the coding agent. _on_step_end passes agent_note(model_output) (the step's evaluation, memory, and next goal, each once) to _record_memory_results, which stores it on each flow step that step recorded; flows keep it, so replayed steps carry the note of the run that first took them. The engine writes no test script: the coding agent writes the test in the repository's language, and ForgeQE runs it.

#Bridge (src/engine)

The launchers (bin/forgeqe.js for npm, py/forgeqe_cli/launcher.py for pip) use a Bun 1.3+ from FORGEQE_BUN, PATH or ~/.bun/bin, else download the pinned BUN_VERSION from Bun's GitHub releases into ~/.forgeqe/tools/bun-&lt;version> after checking it against SHASUMS256.txt. Both pin the same version (a test checks this). The pip launcher runs the checkout's src/index.ts when it sits in the repo, else bun x ForgeQE@&lt;its version>.

src/tools.ts downloads a release archive into ~/.forgeqe/tools/&lt;name>-&lt;version>, checks its SHA-256 (from the release's checksum file, or the digest GitHub's release API records), unpacks it with tar (System32's bsdtar on Windows, which reads zip), and removes older versions. uv and the agent runtime use it; the launchers carry their own copy for Bun because they run before any TypeScript. code/runtime.ts uses the runtime from code.runtime, PATH, or an existing install, else downloads the pinned runtime, whose version matches the agent runtime SDK in package.json (a test checks this). forgeqe setup calls it, and so does every command that can start the agent.

setup.ts finds or creates the engine environment: FORGEQE_PYTHON when that Python passes the engine check (otherwise it logs why and skips it), else ~/.forgeqe/engine/.venv, which is rebuilt when its engine check fails (created with uv venv --python ">=3.11", or python3.11+ -m venv when no uv can be found or downloaded). uv is the system one, else the pinned UV_VERSION downloaded from uv's GitHub releases into ~/.forgeqe/tools/uv-&lt;version> (checked against its .sha256, unpacked with tar, which on Windows is System32's bsdtar). A downloaded uv keeps the Pythons it fetches in ~/.forgeqe/tools/python. It installs the engine's pinned Python libraries and records the version in installed.json, so later runs skip setup. When Google Chrome is missing it installs Chromium through Playwright.

#Containers (src/containers)

containers: in forgeqe.yaml declares services (config.ts). It refuses any setting outside the fixed list, an image without an exact version, a port bound to an address other than 127.0.0.1, and a mount option.

  • run.ts finds docker or podman and builds run arguments:

    • ForgeQE's labels;
    • --security-opt no-new-privileges and --pids-limit;
    • --publish 127.0.0.1:…;
    • --env NAME for secrets;
    • :ro mounts.

    It checks mounts as uploads are checked (inside the project; nothing hidden, key-named or linked). It waits for a TCP or HTTP ready check. Docker's port proxy accepts connections before the service listens, so a TCP connection counts only when it stays open. It scrubs secrets from logs and errors, and tracks the containers it started, which the CLI removes on exit.

  • mock.ts makes WireMock stubs from network.json or a contract set.

  • compose.ts translates docker-compose services into forgeqe.yaml services, refusing settings that widen what a container reaches. startOrder (config.ts) orders services by depends_on. Every container joins the project network forgeqe-&lt;key> under its service name.

  • tests.ts is a runTestCommand for run_tests with containers.tests. It runs the confirmed command with sh -c in the image, with the repository mounted at its own path, --user this machine's user, and only the environment's FORGEQE_* variables, the saved-login variables, and the listed env and secrets, by name. The repository's credential files are covered (masks.ts), and docker top finds the browsers the test launched.

  • workspace.ts is containers.workspace. loadConfig registers it for the repository (active.ts). Nothing starts until openSession or runTestCommand asks for it. Then one container per process and project waits (sleep infinity) with the repository, the home volume forgeqe-&lt;key>-home and the project network. openSession sets the agent runtime's SHELL to a script that runs exec --workdir "$PWD" … sh -c "$2" in it, refuses a folder outside the repository, and adds workspaceNote to the agents' instructions. It starts Chromium on 127.0.0.1:9222 inside, headless or on Xvfb, and a gateway on 9223 that pipes a connection only when the path starts with the random token (constant-time compare) and any Origin is local. The token goes to the runtime by name. #Databases, test data and data flows (src/data, py/forgeqe_data)

databases: in forgeqe.yaml, or in the active environment of env.yaml, names the databases (config.ts): Postgres, CockroachDB, Redshift, MySQL, MariaDB, SQL Server, Oracle, SQLite, DuckDB, Snowflake, MongoDB and Kafka.   • The guard: guard.py parses every statement with sqlglot in the database's dialect. A read is exactly one SELECT, SHOW, DESCRIBE or EXPLAIN SELECT.   • Data flows: flows.py checks the hops listed in flows.yaml (beside forgeqe.yaml), from a source table to a target table, by batch or in real time. streams.py reads Kafka topics and HTTP APIs as hops. flowreport.ts writes flows.json and report.html to &lt;reports>/flows-&lt;time>/, and flowado.ts posts the results as an Azure DevOps test run.

  • The agent's tools are databases, database_schema, run_sql, generate_test_data and test_data_batches (src/mcp/datatools.ts), and data_flows, check_flows, trace_record and read_mapping_file (src/mcp/flowtools.ts). #Profiles and the offline test double
