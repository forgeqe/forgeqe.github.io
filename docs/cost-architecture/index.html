Cost-aware execution

Status: proposal · 2026-10-15

ForgeQE pays the model for work it has already done. This document sets out how ForgeQE decides when the model is needed at all, and how much of it. The approach is built from published, measured techniques. The goal for known work: a rerun of an existing test costs 0–5% of its first run, and the model is paid only for what is new or broken.

#1. What a request costs today (measured)

From the session logs in a live project (.forgeqe/logs, Azure OpenAI gpt-5.4):

RequestAgent callsInput tokensOutput tokensCached
"Are we ready to release?" (one release-readiness tool call)12577K2.6K518K
Test-authoring sessionmany1.9M8.9K1.65M

These numbers show three things:

  1. Fixed overhead per call. Every chat-agent call resends about 45K tokens of system prompt, tool definitions and history. Output is under 0.5% of tokens, so the cost is the context, not the work.
  2. Calls multiply. The deterministic release check took 12 calls, because the agent asked questions, searched for files, read config and summarised.
  3. Known work is not recognised:
    • Every request goes through the chat agent, including the rerun link.
    • Page memory finds a saved flow only by the exact goal text plus the URL (memory.py: goal_key), so a reworded goal misses it.
    • replay: verify replays every step, then starts the browser agent to check the result.

Prompt caching already works (about 90% of input is cached). It lowers the price per token, but not the number of tokens or calls, so on its own it cannot reach the target.

#2. The approaches this design uses

TechniqueEvidenceWhere it applies here
Workflows before agents. Use fixed code paths for predictable tasks; keep agents for open-ended ones.Anthropic, Building effective agents (2024)Tier 0: rerun, run case, run suite, release check
Plan caching. Extract a plan template from a finished run, match new requests by key, and adapt the template with a small model.Zhang et al., Agentic Plan Caching, NeurIPS 2025: 50.3% lower cost and 27.3% lower latency on average, performance maintainedTier 1: known flow, new wording or new data
Workflow memory. Turn successful trajectories into reusable routines.Wang et al., Agent Workflow Memory, ICML 2025: +51.1% relative success on WebArena, fewer stepsFlows saved from passing runs, shared across cases
Model cascade and routing. Try the cheapest model or step that can answer, and escalate only when a check fails.Chen et al., FrugalGPT (up to 98% savings, task-dependent); Ong et al., RouteLLM, ICLR 2025 (over 2x savings at about 95% quality)The router; result checks on the reviewer model
Content-addressed memoization. Key cached work by a fingerprint of its inputs; any change to the inputs invalidates it.Standard in build systems (Bazel, Gradle remote cache) and in test impact analysisRegistry fingerprints, the tool-result cache
Record–replay with self-healing locators.Already in ForgeQE (replay.py, ranked locators)Tier 0 and Tier 2 execution

The published figures come from the authors' own benchmarks. ForgeQE has to measure its own (section 7).

#3. The execution ladder

Every request is resolved to the lowest tier that can do it. A tier escalates only on a concrete failure signal, never on a guess.

TierWhenModel useTarget cost vs. first run
0: DeterministicThe request resolves to a known entity, and replay and end-state checks passNone. The reply is filled in from the result.0%
1: AdaptA known flow, but with new wording, new test data, or an end-state check that is unsureOne call to the small (reviewer) model with a short prompt (about 2K tokens)≤5%
2: HealReplay stopped at step k, or a check failedThe agent starts at step k with the steps so far as context, not from the beginningProportional to what broke
3: ExploreNo match in the registry: a new goal or new kind of taskFull agent, as today100%
text
request ──► Resolver (no model) ──hit──► Tier 0 run ──checks pass──► reply from template
               │                            │ checks fail / replay stops
               │ ambiguous                  ▼
               ▼                         Tier 2 heal (agent from step k)
         Router (small model, ~2K) ──known──► Tier 1 adapt
               │ novel
               ▼
         Tier 3 full agent ──passes──► registry learns the flow, plan and checks

Resolver (no model). Matches IDs (TC-123, SHOP-12, plan/suite numbers, run folders, last), file and test names, and aliases from the registry. The rerun link and /rerun call it directly. Plain requests try it before any model is called.

Router (small model). Runs only when the resolver is unsure. It sees the request and the top registry candidates (ranked by alias and keyword match), not the full tool catalogue. It returns {entity, tier} or novel.

Safety rules (non-negotiable):

  • A Tier 0 pass needs evidence: replay complete and every recorded end-state check passing. Anything else escalates.
  • Freshness. A flow is marked stale when the app changes: a new deploy or build id (when configured), a changed page fingerprint seen during replay, or the age limit (registry.maxAgeDays). A stale flow runs at Tier 1 once to re-confirm it.
  • Canary. Every Nth Tier 0 run of an entity (default 10) runs at Tier 1, so a check that silently passes is caught.
  • The user can always force a tier: /rerun --verify, /rerun --fresh.

#4. The registry: one indexed catalogue

The registry is one SQLite file per project: .forgeqe/registry/registry.db.

  • Bun ships bun:sqlite and Python ships sqlite3, so there are no new dependencies.
  • It is local, and git-ignored by default (its folder carries its own .gitignore).
  • Existing JSON stores (page memory, code graph, quality history) stay where they are. The registry indexes and links them, it does not replace them.

#4.3 Fingerprints and invalidation

A cached item is valid only while its fingerprint matches its source:

  • test_case: hash of the normalised steps plus expected results, together with the ADO rev. This replaces matching on goal text, so rewording a request no longer misses the flow.
  • code_test: git blob sha of the test file and of the page objects it reaches (from the code graph).
  • flow: hash of its steps, together with the page fingerprints seen on its last pass.
  • tool_cache: the source's own version (work item rev, sprint id, ETag) where one exists; otherwise a short TTL. Writes always bypass it.

#5. Building context (for Tiers 1–3)

The agent's fixed 45K-token context is the main cost driver. Context is built from the registry instead of being discovered by the agent:

  • Context packs. For each entity, a brief of a few hundred tokens: what it is, its linked case, code test, flow, pages and last results. The agent gets the brief rather than spending calls on read, grep and code_outline.
  • Tool listing by tier:
    • Tier 1 gets one tool.
    • Tier 2 gets the tools of the capability that broke.
    • Tier 3 gets today's progressive listing (routing.ts).
  • Stable prefix first, variable last, so prompt caching keeps hitting.
  • History compaction. After a request finishes, only its outcome and ids are carried forward, not its tool results.

#6. Learning: how the registry fills itself

  • Indexing.
    • On forgeqe init, and incrementally on file change, the code graph and cases sources are indexed into entities, aliases and links.
    • ADO and Jira items are indexed when they are first fetched.
  • Promotion. A Tier 2 or Tier 3 run that passes, and passes the judge when it is on, writes or updates its plan and checks. A plan needs two passes, or one pass plus user confirmation, before it is allowed to run at Tier 0.
  • Demotion. Failures increment failures. Two failures in a row mark the plan stale, and the next run goes to Tier 1 or 2.

#7. Measurement and acceptance

The ledger (runs) makes cost measurable per tier and per entity. forgeqe cost reports the following metrics. Each must meet its target before a phase counts as done.

MetricTarget
Cost of a rerun of a known passing test, vs. its first run≤5% (Tier 0: 0 tokens)
Share of reruns served at Tier 0 or Tier 1≥90%
Tier escalation rate on unchanged apps≤5%
False pass rate (Tier 0 pass that a Tier 1 canary then fails)0 known; every one investigated
Release check ("are we ready", scope known)0–1 agent calls

The evaluation is an offline replay suite under src/evals. It holds recorded requests (rerun, reworded rerun, changed app, new goal), each with an expected tier and outcome. It runs on every change to the resolver, router or registry, and live against the real model before release.

#8. Compatibility and rollout safety

Nothing here may change what ForgeQE does today until it has been shown to give the same results.

Built alongside, never in place of

  • registry.mode: off | shadow | on in forgeqe.yaml. It defaulted to off through phases 1 and 2, and to on from 2026-10-15, after the live results in sections 9–10. With off, every request takes the agent's path, unchanged.
  • The new code lives in src/registry/. Existing modules gain only small hooks at their entry points: the chat request handler, the command parser and config. The chat agent, page memory, replay modes and tools keep their behaviour.
  • Any registry error (missing, locked or corrupt database, an exception in the resolver) falls back to today's path. The registry is a cache: deleting it loses savings, never behaviour.
  • Existing stores (page memory, code graph, quality history, run folders) keep their formats. The registry reads and indexes them and never writes to them.
  • Tier 0 runs through the same browser_run tool the agent calls. Existing-test reuse, page memory replay, the configured replay mode, reports and quality checks all apply as they do today.

Proven before it is switched on

  • Tests that lock in today's behaviour. Written before the hooks, they pin down today's results: a request with the registry off goes to the agent, and the rerun link goes to the agent. They have to pass unchanged afterwards.
  • Shadow mode. The resolver decides and records what it would do (runs with mode = shadow), while the request still takes today's path. The decisions are compared with real outcomes before on.
  • False pass check. During rollout, every Tier 0 pass is re-checked at Tier 1. Any disagreement blocks the next phase.
  • The full suite. Every existing test passes unchanged in every phase, with no existing test edited to make it pass.

Switched on gradually

  • One phase per release. Each one can be turned off on its own.
  • A live check against the real model, Azure DevOps and Teams before each phase is called done.
  • Every reply says which tier answered it. /rerun is an explicit command, and the agent remains one sentence away: anything the resolver is unsure of goes to it.

#9. Phase 1 live result (2026-10-15)

Live run against Azure OpenAI gpt-5.4 and a real headless Chrome: a /rerun of a 27-step practice-form run whose first run used 242K tokens.

Result

The remaining cost is the browser agent's check after replay. Phase 2 is the step that reaches the target. Read-only steps (evaluate, extract) and the final check must be answered from recorded end-state checks (run.json already records checks with expected values). The agent comes in only when a check fails.

#10. Phase 2 live result (2026-10-15)

What phase 2 adds, with registry.mode: on only:

  • evaluate steps whose script only reads the page are left out of a replay. The test is on the script's source and conservative: any assignment, any page-changing call, any request or deferred code counts as writing. Checked against every evaluate in a live project's flows: no write was classed as read-only.
  • A passing run's record_check results are kept in its flow, each with the step it was recorded after.
  • A replay finds each check on the page again after that step, with no model. If every check holds, the run passes with no model. The first check that does not hold stops the replay there, and the agent takes over on that page (today's path).
  • The agent still judges the run when: a check is dynamic, the flow has not passed for 30 days, or it is every 10th replay of the flow (the canary).

#12. Per-turn tool scope (2026-10-17)

Tool definitions are part of the fixed overhead in section 1, and they grew with the desktop, mobile and TestMu tools. The forgeqe agent's fixed context went past its budget. ForgeQE's agent now gets the tools of the capabilities a turn needs, not all of them (src/mcp/scope.ts; see ARCHITECTURE.md):

  • Every turn: the core (help and setup, use_capabilities, the test environments and their apps).
  • Picked without a model call: up to four capabilities matched from the request's words, the apps it names, its links and issue keys. A capability the project has no apps or tracker for is not picked from words alone.
  • Sticky: capabilities whose tools ran in the last three turns.
  • On request: use_capabilities adds one when the request turns out to need it, and ForgeQE continues the same request.

forgeqe context, measured on this repo:

Tokens
The forgeqe agent's fixed context (prompt 6.2K + core tools 1.6K)7.8K of a 10K budget
A turn with the four largest capabilities14.7K
Every tool on every turn (FORGEQE_TOOL_SCOPE=off)about 26.7K
Largest single capability (api-testing, systems)1.8K of a 2.5K budget per capability

A typical turn ("replay the courier login on Maestro") adds one or two capabilities, around 1–3K. Beyond the cost, fewer tools in view keep the agent from mixing up similar ones (browser_run, desktop_explore, mobile_explore). The test tests/agents.test.ts fails when an agent or a capability passes its budget. That keeps new tools from bringing the fixed overhead back.

Still to measure: live-model evaluations of the tool picks against FORGEQE_TOOL_SCOPE=off: the success rate, the use_capabilities calls per request, and tokens per request.

#13. Page memory at every step (2026-10-21)

A suite run in a live project (three Toolshop cases, Azure OpenAI gpt-5.4) showed why a rerun of a known case still cost what its first run did:

RunModel stepsInput tokensReplayed
ADO-3287, first run (an expected result did not hold at step 7)1188K0
ADO-3287, the reproduce run straight after29243K0

Each model step costs about 8K input tokens, 6.3K of it the cached system prefix: the live page is a small part. So page memory can only lower cost by taking steps away from the model, and two things kept it from doing that:

  1. A failed case saved nothing to replay. resume steps were kept for errors only; a run that failed because an expected result did not hold (assertion_failed, which is what a reproduce run or a rerun of a failing case is about) saved no steps, and the next run explored the whole case again. Now the steps up to the first check that did not hold are kept (assertion_resume, marked assertion: true), the next run replays them, and the handoff tells the agent to check that result again where it is, not to redo the steps or try to make it true.

  2. Known controls were described, not addressable. The site-memory hints in the system prompt named the controls earlier runs used, but an action needs the element's index in this step's list, which changes with every page load, so the agent read the whole list anyway. Now each page memory knows gets a note after the element list, before the model call, naming up to 10 controls earlier runs used with the index each has right now (MemoryStore.known_controls, through the library's per-step context messages). The page is observed once per step and that snapshot also scores the step's actions.

  3. A replay to a failed check handed the check to the agent. The page that failed often shows its message only briefly (a toast), so it was gone by the agent's first step, and the agent spent six steps looking for it (live: 49.5K tokens, more than the first run). Now, with registry.mode: on and replay: verify, the run looks for the text the page showed instead right after the replay, with no model (reproduced_by_check). Finding it again fails the run the same way at 0 tokens; not finding it hands over to the agent as before. A failure text that a passing check of that run also found (a heading, the product name) is never kept for this, since it shows whatever the outcome.

Live, Toolshop, headless Chrome, Azure OpenAI gpt-5.4, a clean memory folder:

RunModel stepsTokensResult
A: first run of a 3-step case whose last expected result does not hold537.1Kfailed; kept the 3 steps up to the failed check
B: the same case again (a rerun or reproduce run)00 (5 s)replayed 3 steps, found the same failure text, failed the same way

#13.1 Every case, every area (2026-10-21)

The same project's history showed the wider gap: of 20 recorded web runs only 4 replayed anything (2.7M tokens in all), almost every miss a goal worded differently from its flow. Mobile and desktop explores never read what an earlier one saved, desktop and mobile heals were found again on every replay, API plans were made again for the same cases, and only browser goals could be rerun without the agent. What now holds in every area:

AreaBefore the model is calledNo model at all when
Browserthe goal's flow, its failed-run steps, an edited case's unchanged steps, else the start it shares with another goal on the host (flowmatch)checks of a replayed flow hold (section 10); a failed check shows the same failure text again
Mobile, desktopthe goal's workflow, its failed-run steps, else the shared start in the app (app memory); known controls marked for the modelthe goal's workflow replays and its checks hold
