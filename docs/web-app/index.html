The web app

forgeqe web opens ForgeQE in your browser: the same agents as the shell, with a chat on Home, pages for recordings, runs, reports, API tests, quality, data, regression packs and schedules, and every setting as a form. It runs on your computer only and works on one project folder at a time, as the CLI works in the folder it is started in.

#Starting it

sh
forgeqe web                           # in a project folder, or anywhere

It opens in your default browser and prints its address, such as http://127.0.0.1:53817/#token=…. In CI, on a Linux machine without a desktop, or with --no-open, it only prints the address: open it yourself. When it does not open the browser, or the browser could not be opened, the next line says why. The page keeps the token for that browser tab only; another tab, or the page after the token is gone, says it is signed out: open the printed address again. Ctrl+C in the terminal stops it.

OptionWhat it does
--port NA fixed port instead of a free one, for a bookmark or when a port is taken.
--config forgeqe.yamlWork on the folder of that file.
--no-openPrint the address without opening the browser.

#The first time: Set up

The first page is Settings › Set up, in four steps. Until the folder has a forgeqe.yaml, the other sections of Settings are locked.

  1. Project folder. The folder ForgeQE works on: browse to it, type its path, or make a new folder. It can be a clone of your test repository (tests written from passed runs go there), a clone of the application, or an empty folder to try ForgeQE in. ForgeQE does not clone repositories: clone with git first, then pick the folder.
  2. ForgeQE in this folder. The same as forgeqe init: forgeqe.yaml, llms.json, the environment files and a .forgeqe folder with prompts, skills and guardrails to change. Files already there are kept, and .forgeqe/reports/ is added to .gitignore.
  3. This computer. What ForgeQE runs with (the browser engine and the agent runtime), with Install what's missing, which runs forgeqe setup and shows its output.
  4. A model. At least one model with its key or sign-in, under Models. For a GitHub Copilot seat, sign in here or in Models (below).

Signing in to GitHub Copilot (Set up, and Settings › Models › Sign-ins) does what forgeqe auth login copilot does. Sign in with GitHub runs GitHub's own Copilot CLI sign-in (downloaded the first time): the page shows GitHub's link with Open GitHub and the one-time code with Copy, and waits while you approve on GitHub; the sign-in stays in the system's credential store, and ForgeQE handles no token. Use a token is for a machine without a browser: a fine-grained github_pat_ token with the Copilot Requests permission, typed into a password field and kept in the credential store; no response shows it back, and a classic ghp_ token is refused. Either way ForgeQE then lists your seat's models, you pick one, and the Copilot profile in llms.json becomes the default. The card says who is signed in and how, with Sign out.

Next time, forgeqe web opens the folder it is started in when ForgeQE is set up there, else the last project opened (it keeps the last ten).

For a team. One person sets ForgeQE up in the shared test repository and commits what it made: forgeqe.yaml, the environment files, llms.json, and the team's guardrails, prompts and skills under .forgeqe/. Everyone else clones the repository, runs forgeqe web in it, and adds their own keys in Settings. Keys and passwords never go in those files: each person's are in their own credential store.

#The layout

  • The sidebar, on the left. New chat (opens Home, where a chat starts; earlier chats are in Runs); Agents: a page for each of ForgeQE's agents (Orchestrator, Browser, Exploration, Planning, Coding, Search, Healing, API, API planning, Review, PR review, Root-cause, Refine, Evaluation, Model-rating, and the Research and Helper agents the others call), in categories that fold on their own: Lead, Browser, Test code, API, Review and diagnosis, Support; Context (what the agents know and follow): Knowledge, Memory, Guardrails, Skills, Prompts; Test: Record, Regression, API tests, Quality, Data; Results: Runs, Reports, Jobs. Each group folds from its title (Agents starts folded), and the group of the page you are on stays open; and at the bottom What's ready, Help (the docs, the same pages as forgeqe.github.io/docs/ with the architecture map, served by ForgeQE itself, so they work offline) and Settings. It closes to a narrow rail of its icons (each named when you point at it), with the small logo on top, to give the page the width; on a phone it is a drawer.
  • The workspace panel, on the right. The project, its repository and branch, and the test environment; the context and tokens of the chat and of the project, in your local currency (pounds in the UK, from the European Central Bank's daily rates); the background tasks running now; the files a chat changed, with Create pull request; and what it produced (reports, tests, recordings), under the Capgemini logo. It sits beside the page on a wide screen (1600 pixels and up); on a laptop it opens over the page, so the page keeps its width. Where it is not beside the page, a narrow rail of its sections' icons is: one opens the panel at that section.

#Home and a chat

Home is one box: say what to test, in your words. Under it, suggestions (Run test cases, Explore a journey, Write a test, Review requirements) fill the box with an example; they do not send.

An agent's page (Agents, in the sidebar) is the same box with the agent's icon, its name and what it does on top, suggestions of its own, Tools it can use (the first five groups, folded, with Show all to its tools page, #/agents/&lt;agent>/tools, which lists every group and tool open; its own tools with what its permissions take away, and each tool server its session gets: the live browser, the code map, databases, ForgeQE's tools, and for the Orchestrator agent every capability and your systems' MCP servers; a group it cannot use here says why), Connected to (the test repository, databases, test environments and systems it reaches), its instructions (the prompt it starts from, changed in Prompts) and its recent runs. A request sent from there goes to the Orchestrator agent with the agent's name before it, so it is handed on.

Every page and agent in the sidebar has one kind of icon, ForgeQE's 3D pixel icons; a page's is never an agent's. Sidebar icons in Appearance says how they sit on the sidebar's colour: Auto measures every icon against it and keeps them as they are when each stands out (2:1), or puts them all on tiles in a tint of the sidebar when the colour hides any; or a brand chooses one look: Plain, On tiles, Outlined, or One colour (the icons' shapes in the sidebar's text colour). The row previews the look and names the icons that fade.

In the box:

  • Tools: whether this chat writes the test into the repository and shows the browser, and what comes from the settings (where browsers run, where test cases come from). They can be changed in a chat that has started.
  • The model: Auto routing, or one of your models.
  • Attach: files for the agent to read.
  • Refine: rewrites your request precisely against what ForgeQE knows here, in the same box, without running anything; Undo puts your words back.

A reply shows the work as it happens:

  • The plan as a chain: what is done (a tick), what is being worked on now, and what is next.
  • The agents: each step under the agent doing it (the Orchestrator agent, the Browser agent, the Coding agent), and each handoff from one to another.
  • The latest activity, live, with the full log a click away.
  • The result: each test with its status, file and the command to run it; reports as links; every file changed with its diff.
  • Next steps as buttons (run it on another browser, open a pull request, investigate a failure), each a new request in the chat.

Stop ends the work in progress. While the agent works the page follows the latest step; scroll up and it stops following, and Latest activity takes you back.

All chats (#/chats, and each web chat from Runs) lists every chat since forgeqe web started, newest first, grouped by day: Working, Needs you, Your turn and Ended as filters, a search, and 50 at a time.

#The pages

PageWhat it is for
RecordDo a test's steps yourself in a browser or a Windows app ForgeQE opens; each click, entry and check is recorded. A web recording becomes a test through a chat; a desktop one replays with no model. The recordings, searched and paged.
RegressionRegression packs for a release: built from test cases, run, and healed, with their results.
API testsContract sets from an API description or the calls a browser run saw; scenarios that chain calls. Run them (calls that change data only after you agree), see each call's result, write them as tests.
QualityWhat each browser run measured: accessibility (WCAG), Core Web Vitals, and visual changes against approved baselines, with Approve as the new baseline; and each page's trend.
DataDatabases (read-only queries; test data only with a writable database and your confirmation), test data, and data flows.
RunsEvery ForgeQE session in the project, from here, a schedule or the terminal: 25 to a page with filters. A run shows its summary, the conversation, its activity, and its details.
ReportsEvery report ForgeQE wrote, each opening as its HTML report in a new tab; and the project report: every run together, with pass rate by day, what fails most, flaky cases and defects.
JobsScheduled and long jobs (the jobs service): their runs, logs and alerts.
KnowledgeWhat the agents know about your product, and adding to it.
MemoryWhat ForgeQE learned from runs that passed, by site: flows replayed without a model, and pages with their elements. Clearing a site's memory asks first.
GuardrailsThe rules every agent follows.
SkillsWhat the agents know how to do, by the agents that use them; add, edit and remove the project's own.
PromptsThe instructions each agent starts from, with the agents that use each; edit one, or add your team's own for chosen agents.
What's readyEach capability, whether it is ready here, and what it still needs.

#Reports the agent writes

Ask for a report in a chat ("a report of all open defects", "release status for all projects") and the agent writes one from the results of the calls it made. The report has three pages: Overview (the summary, and when the rows are work items: how many are open, critical and high, unassigned, how old, untouched for 30 days, the ones that need someone now, and charts by project, person, age and week), the rows with filters and a CSV export, and Sources, each call the rows came from. The analytics are worked out from the rows; the model writes none of them. See Reports from the agent.

#Settings

Settings takes over the window: one menu on the left, with Back to ForgeQE and Search settings (by name or forgeqe.yaml key), and the sections under General, AI, Testing, Activity and Advanced. Each setting shows its forgeqe.yaml key under its help.

Appearance gives the web app the project's look, for everyone who opens it: a logo (PNG, JPEG, WebP or SVG) and a name for the sidebar, the sidebar's colour (primary, with an optional second colour it fades into), and the colour of buttons, links and selection (secondary), with lighter and darker shades made from it. The page itself stays white, and text on each colour turns white or dark so it reads; the section shows the contrast. A square or round logo shows with the name beside it, a wide one alone; Logo frame keeps it as it is, rounds its corners, cuts a square one to a circle, or puts it on a white tile (for a dark logo on a dark sidebar); Logo size Large gives a wide logo the whole top of the sidebar, for one whose words are small. Small logo is the square or round one the narrow sidebar shows; without one, a square logo is used, else the name's first letter. When the logo is the sidebar's colour (its own background, or a shape's ink), it sits on a plate that stands out from the sidebar, and the section suggests another sidebar colour. From a website reads a public site's page and stylesheets and suggests its colours (its header or brand colour for the sidebar, its buttons' for the buttons; never its logo); nothing changes until Use these colours. Only sites on the internet are read, never this computer or a private network. Choose a DESIGN.md fills the colours from a design file. It is saved under theme: in forgeqe.yaml; Back to ForgeQE's look removes it.

Environments lists each environment with Edit and Remove; adding or editing one opens a panel with its name, apps, values, secrets and Test data (the files its tests read, through FORGEQE_DATA_&lt;NAME>). Start from your team's YAML fills the panel from YAML in any layout: Paste it, Import a file from your computer (copied into the fields), or Link a project file (read from that file every run; the panel shows what ForgeQE reads from it, and Copy into fields instead converts it). Secret values in the YAML are never copied.

Changes save themselves. A key or password typed in Settings goes to your credential store under its variable's name, never into a settings file, and is never shown again. Files shows each settings file as text for what the forms do not cover. Every option in forgeqe.example.yaml has a field.

#Safe by design

  • It listens on 127.0.0.1 only, with a random token checked on every call, and refuses requests from other sites.
  • Nothing a page shows is taken as HTML: replies, tickets and reports are drawn as text and links, and a link opens only when it is a web or mail address.
  • A file a reply names opens through a short-lived link in its own sandbox, so a report's scripts never reach the app.
  • Commands the pages start are built from fixed lists of what is allowed; anything that changes data, costs model calls or posts outside asks first.

#When something is wrong

You seeWhat to do
The page says it is signed outOpen the address forgeqe web printed again; each tab needs it once.
The port is in useforgeqe web --port 4711 (any free port).
Settings sections are lockedSet up ForgeQE in the project folder first (Settings › Set up, step 2).
A chat cannot startSettings › Set up, steps 3 and 4: install what is missing, and add a model with its key.
